## Цель проекта
Веб-сервис, в котором продавец загружает обычное фото товара и получает готовый продающий
контент: набор студийных изображений в выбранном сценарии показа или целиком карточку товара
(карусель + заголовок + описание). Снимает необходимость в съёмке, студии и дизайнере.
Генерации складываются в личный каталог, оплата — внутренними баллами.
Подробно — [`../../docs/TZ.md`](../../docs/TZ.md) §1.

## Архитектура (верхний уровень)
React-SPA (TypeScript, Vite) работает напрямую с Supabase: Auth (email + пароль), Postgres с
RLS для чтения своих данных, Storage для фото и результатов, Realtime для статуса генерации.
Отдельного бэкенд-сервиса нет. Всё, что нельзя доверить браузеру — вызов AI-провайдера и
любое движение баллов — живёт в Edge Functions (Deno) с service-role. Генерация асинхронная:
заявка возвращает `generationId`, статус живёт в БД и переживает перезагрузку страницы.
Схемы — [`../../docs/VISUALS.md`](../../docs/VISUALS.md) V-02, V-03, V-07.

## Основные подсистемы
- **Генерация** — мастер сборки параметров (фото → распознавание → тип → сценарий → пожелания
  → количество), справочник 7 категорий и 24 сценариев показа, асинхронное исполнение и
  каталог результатов.
- **Аккаунт и биллинг** — регистрация/вход/восстановление пароля, баланс в баллах, журнал
  операций `ledger`, пакеты пополнения (без эквайринга).
- **AI-слой** — абстракция `ai-provider` из четырёх операций (распознавание, изображения,
  тексты карточки, название генерации) + заглушка для локальной разработки.

## Принятые решения / ограничения
- Стек зафиксирован ТЗ: React.js + Supabase; собственного бэкенда не заводим —
  [ADR-0006](../../docs/adr/0006-supabase-as-backend.md).
- AI-провайдер **не выбран**, код от него изолирован —
  [ADR-0005](../../docs/adr/0005-ai-provider-abstraction.md).
- Эквайринга нет: пакет выбран → баллы зачисляются мгновенно (ограничение ТЗ).
- Вход только email + пароль; типов генерации ровно два («фото», «карточка») — видео из
  референса не делаем.
- Баланс меняется **только** сервером и **только** вместе с записью в `ledger` с ключом
  идемпотентности; RLS включается в той же миграции, что создаёт таблицу.

## Дорожная карта (вехи)
- [ ] **M1 — Каркас и аккаунт.** Проект собирается, регистрация / вход / восстановление
      пароля работают, профиль показывает баланс, при регистрации начисляется N баллов.
- [ ] **M2 — Биллинг.** `ledger`, идемпотентное списание и возврат, пакеты пополнения,
      RLS-тесты «чужой id → отказ». Делается **до** генерации: переделывать деньги после
      запуска дороже всего.
- [ ] **M3 — Генерация сквозняком на заглушке.** Мастер, справочник категорий и сценариев,
      асинхронная генерация со статусом, результаты, скачивание, каталог. Провайдер —
      заглушка: сценарий проверяется целиком, не тратя бюджет.
- [ ] **M4 — Реальный провайдер.** Выбор вендора по способности сохранять предмет с фото,
      реализация `ai-provider`, распознавание и тексты карточки, учёт себестоимости, новый ADR.
- [ ] **M5 — Наполнение и приёмка.** Все 24 сценария показа, сценарии ошибок US-E1…US-E7,
      критерии приёмки релиза (`docs/TZ.md` §9).

> Порядок M2 → M3 не случаен: биллинг — фундамент, а генерация на заглушке позволяет
> закрыть весь пользовательский путь до того, как выбран провайдер.
