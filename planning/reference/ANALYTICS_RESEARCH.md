## 1. Разделение, из которого всё следует

Разведка подтверждает постановку плана: это **две подсистемы**, и ни один инструмент не
закрывает обе одинаково хорошо.

- **Продуктовая половина** — события, воронки, пути, реплеи. Здесь есть «один вместо
  четырёх»: PostHog.
- **Инженерная половина** — логи, метрики, трейсы, ошибки. Здесь есть стандарт транспорта
  (OpenTelemetry) и сменяемые бэкенды за ним.

**Склейка половин — сквозной идентификатор.** Стандартный, а не самодельный: W3C Trace Context
задаёт HTTP-заголовки `traceparent` / `tracestate`. Формат `traceparent` — `version "-" trace-id
"-" parent-id "-" trace-flags`, пример `00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01`
(32 hex-цифры trace-id, 16 — parent-id). Статус: **W3C Recommendation от 23.11.2021**, то есть
это норма, а не соглашение одного вендора.
[Первичный: [W3C Trace Context](https://www.w3.org/TR/trace-context/)]

> **Берём в ADR-T0006:** корреляция клиент↔сервер строится на `traceparent`, а не на собственном
> заголовке. Собственный идентификатор сессии (`session_id` / `distinct_id`) продуктовой
> половины **дополняет** его, а не заменяет: у продуктовой половины другой срок жизни объекта
> (сессия ≠ запрос).

### 2.1 PostHog — покрытие и цена

- **Бесплатный тариф облака (сверено 2026-09-04):** «1M events» аналитики, «5K recordings»
  session replay, «1M requests» feature flags, «100K exceptions» error tracking, «10 GB
  ingested» логов, «1M rows» data warehouse — **на каждый продукт своя отдельная квота**.
  [Первичный: [posthog.com/pricing](https://www.posthog.com/pricing)]
- **Что происходит при исчерпании без карты:** «Usage stops at the free tier limits, so you
  can't be charged by surprise» — то есть приём **останавливается**, а не тарифицируется молча.
  [Первичный: [posthog.com/pricing](https://www.posthog.com/pricing)]
  > Для stage это ровно то поведение, которое нужно: мусорный трафик упирается в потолок и
  > не превращается в счёт. Но он же означает **дыру в данных**, если общий проект с продом —
  > отсюда требование плана «stage не делит с продом ни проект, ни квоту».
- **Цена за единицу сверх free tier:** ≈ `$0.00005` за событие аналитики с понижением ставки
  по объёму; session replay — ≈ `$0.005` за запись на первой ступени (5K–15K) с понижением до
  ≈ `$0.0015` на больших объёмах. **[вторичный]** — тарифная лестница на самой странице
  отдаётся JS-калькулятором и в статическом ответе отсутствует; цифры взяты из обзоров 2026
  ([Flexprice](https://flexprice.io/blog/posthog-pricing-guide),
  [StackScored](https://www.stackscored.com/pricing/product-analytics/posthog/)) и **обязаны**
  пересверяться калькулятором на posthog.com перед бюджетным решением.
- **SDK — покрывают все профили шаблона:** официальные библиотеки для JavaScript web, React,
  React Native, Next.js, Vue, iOS, Android, Flutter, Kotlin Multiplatform, Node.js, Python, Go,
  Java, Ruby, PHP, .NET, Elixir, Rust, Unity. Ограничение, важное для профилей `backend-api`,
  `cli`, `data-ml`: «Session recording and autocapture are not possible in server libraries» —
  серверная библиотека шлёт только явные события.
  [Первичный: [PostHog — Libraries](https://posthog.com/docs/libraries)]
- **Резидентность:** PostHog Cloud EU размещён во Франкфурте (AWS `eu-central-1`); для EU-облака
  захват IP по умолчанию отключён для новых проектов. **[вторичный]** — сводка по
  [PostHog GDPR docs](https://posthog.com/docs/privacy/gdpr-compliance) через поиск; прямой
  фетч страницы `docs/data/eu-us-cloud` вернул 404, точную формулировку и возможность миграции
  US↔EU проверять на месте.
- **Self-host — не равноценная замена облаку.** Официальный дисклеймер: OSS-развёртывание
  «made for hobbyists», всё на одной машине, «unlikely to scale past a couple 100ks events
  without significant effort», один проект, без Experimentation / Advanced Paths / Permissions,
  коммерческой поддержки нет. **[вторичный: сводка по
  [PostHog — Self-host disclaimer](https://posthog.com/docs/self-host/open-source/disclaimer)]**
  > **Ключевой вывод, ломающий типовое ожидание:** self-host PostHog **не дешевле и не мощнее**
  > бесплатного облака — он слабее его по возможностям и упирается в потолок раньше, чем в
  > free tier облака. Его единственный настоящий мотив — резидентность данных (§6).

### 2.2 Sentry — ошибки как отдельная дисциплина

- **Free (Developer) тариф, сверено 2026-09-04:** «5k errors», «5M spans», «50 replays»,
  «5GB» логов, «1 cron monitor», «1GB» вложений, «10» дашбордов, один пользователь.
  Team — «$26/mo» (годовая оплата), Business — «$80/mo».
  [Первичный: [sentry.io/pricing](https://sentry.io/pricing/)]
  > **50 реплеев в месяц** — это не «session replay в проекте есть». Для реплеев на free-контуре
  > Sentry не кандидат; кандидат — PostHog (5K) или Clarity (без лимита).
- **При исчерпании квоты события теряются безвозвратно:** «Events and attachments that exceed
  your quota will not be accepted». Есть Spike Protection: при аномальном всплеске «events start
  getting dropped, ensuring that you don't get charged for the excess volume».
  [Первичный: [Sentry — Quotas](https://docs.sentry.io/pricing/quotas/)]
- **SDK:** официальные для JavaScript/React, React Native (+Expo), Apple/iOS, Python, .NET,
  Node.js — «Sentry provides official SDKs for all major platforms and frameworks».
  [Первичный: [Sentry — Platforms](https://docs.sentry.io/platforms/)]
- **Self-host — дорогой по железу.** Минимум: «4 CPU Cores», «16 GB RAM + 16 GB swap»,
  «20 GB Free Disk Space» (рекомендуется 32 ГБ RAM); лицензия FSL (переходит в Apache 2.0 через
  два года), «no guarantees or dedicated support», нет spike protection и spend allocation.
  [Первичный: [Sentry — Self-Hosted](https://develop.sentry.dev/self-hosted/)]
- **GlitchTip — лёгкая self-host альтернатива под тот же SDK:** «Recommended system
  requirements: 512 MB RAM, x86 or arm64 CPU», минимум «256 MB RAM when using all-in-one
  setup», «careful configuration will allow 128 MB + swap»; ориентир по диску — «a 1 million
  event per month instance may require 30GB of disk».
  [Первичный: [GlitchTip — Install](https://glitchtip.com/documentation/install)]
  > **Разница в 32 раза по RAM** (16 ГБ против 512 МБ) — это и есть ответ на «self-host
  > ошибок под 152-ФЗ»: GlitchTip, а не Sentry, если объём позволяет.

### 2.3 OpenTelemetry — то, что делает бэкенд сменяемым

- **Collector — «a vendor-agnostic way to receive, process and export telemetry data»**,
  поддерживает открытые форматы и отправку «to one or more open source or commercial
  backends». Смена бэкенда — правка конфигурации экспортёра, **без изменения кода приложения**.
  [Первичный: [OTel — Collector](https://opentelemetry.io/docs/collector/)]
  > Это техническая основа ADR-T0006 и главный аргумент «слой абстракции = контроль затрат»:
  > для инженерной половины слой абстракции не нужно писать — он существует как стандарт.
- **Зрелость SDK по языкам (сверено 2026-09-04):** .NET и Java — traces/metrics/logs все
  **Stable**; Go — traces/metrics Stable, logs RC; JavaScript (Node и браузер) и Python —
  traces/metrics **Stable**, logs в разработке; **Swift — Stable только traces**, метрики и
  логи в разработке.
  [Первичный: [OTel — Languages](https://opentelemetry.io/docs/languages/)]
- **React Native — дыра в покрытии.** Официального RN-SDK в проекте OpenTelemetry нет;
  доступны дистрибутивы вендоров (Embrace, Honeycomb) и community-библиотеки, часть из них
  помечена экспериментальной. **[вторичный: сводка по
  [Embrace](https://embrace.io/blog/embrace-react-native-sdk-now-fully-built-on-opentelemetry/),
  [Honeycomb RN docs](https://docs.honeycomb.io/send-data/react-native)]**
  > Следствие для профиля `react-native` в `INIT.md`: инженерная половина на клиенте берётся
  > **у вендора** (Sentry RN SDK), а чистый OTel остаётся на сервере. Обещать «один OTel
  > везде» в этом профиле нельзя.
- **Sampling — головной и хвостовой.** Head sampling: «easy to understand, easy to configure,
  efficient», но нельзя гарантировать сохранение всех трейсов с ошибками. Tail sampling —
  «the decision to sample a trace takes place by considering all or most of the spans within
  the trace», позволяет всегда сохранять ошибочные и медленные. Цена: «stateful systems that
  can accept and store a large amount of data», в пределе «dozens or even hundreds of compute
  nodes», и «it is critical to monitor tail-sampling components».
  [Первичный: [OTel — Sampling](https://opentelemetry.io/docs/concepts/sampling/)]
  > **Поправка к плану.** План называет tail-based оптимумом для прода. Разведка это
  > подтверждает *по качеству сигнала*, но добавляет условие: хвостовое сэмплирование —
  > отдельный stateful-компонент со своей стоимостью. Для маленького проекта правильный
  > дефолт — 100% приёма (объёмы влезают в free tier), а tail-based вводится **когда объём
  > трейсов начал стоить денег**, и это записывается в `SPEC.md` как порог, а не как догма.

### 2.5 Локальный приёмник для dev — три годных варианта

Критерий плана: одна команда, без регистрации, без сети, эфемерно.

| Кандидат | Запуск | Что даёт | Вес и старт |

Grafana Cloud.
[Первичный: [grafana/docker-otel-lgtm](https://github.com/grafana/docker-otel-lgtm),

[Jaeger — Getting started](https://www.jaegertracing.io/docs/latest/getting-started/)]

> **Дефолт для dev — `grafana/otel-lgtm`** (все три сигнала, одна команда, in-memory), с

> — это ровно тот вес, из-за которого паритет окружений теряется.
>
> **Ни один из них не требует аккаунта, ключа и сети** — критерий «dev-контур бесплатен по
> построению» выполняется.

## 3. Стоимость тремя колонками

### 3.1 dev — ноль по построению, валюта = RAM и старт

Деньги: **0**, без исключений. Ни один локальный приёмник выше не требует регистрации.

**Продуктовой аналитике на dev бэкенд не нужен вообще.** PostHog-подобная система на dev не
отвечает ни на один вопрос (воронка по трём разработчикам бессмысленна), а нужный ответ —
«событие ушло и с теми свойствами» — даёт тест (шаг 12 плана). Приёмник продуктовых событий на
dev — консоль или файл; это же и есть no-op приёмник из требования плана.

Расход dev-контура — RAM и время старта: otel-lgtm стартует «up to a minute», SigNoz требует
4 ГБ. Именно эти две цифры и должны стоять в стековом профиле `INIT.md`, а не только имя
инструмента.

### 3.2 stage — деньги утекают через квоту, а не через тариф

Все три облачных кандидата имеют бесплатный тариф, покрывающий синтетический трафик stage:
PostHog 1M событий + 5K реплеев, Grafana Cloud 50 ГБ логов, Sentry 5k ошибок. Проблема не в
цене, а в **общей квоте**:

- у Sentry исчерпанная квота = «events... will not be accepted» — прод-ошибки теряются,
  потому что stage выел лимит;
- у PostHog «usage stops at the free tier limits» — то же самое, только в продуктовых данных.

> **Требование к шаблону (в `SPEC.md`, матрица окружений):** stage — отдельный проект и
> отдельный ключ в том же инструменте. Это не экономия, а **корректность прод-мониторинга**.

Чем платим на free-контуре — и больно ли это на stage:

| Что теряем | Больно на stage? |
| --- | --- |
| Retention 14 дней (Grafana Cloud), 15 дней (SigNoz) | Нет — stage-сессию недельной давности никто не разбирает |
| 3 активных пользователя (Grafana Cloud free) | **Возможно** — если QA больше трёх человек, это первый упор в потолок, и не по объёму данных |
| Один пользователь и 50 реплеев (Sentry free) | Нет для stage, **да** если пытаться жить на этом в проде |
| Данные только в облаке вендора | **Да** — при требовании резидентности (§6) |

### 3.3 prod — оптимум, а не минимум

Правило привязки из плана (у каждой статьи есть вопрос, на который она отвечает) разведка
подтверждает численно: дороже всего стоят **сырые высокочастотные сигналы**, а не продуктовые
агрегаты.

Порядок цен на 2026-09-04, приведённый к одной единице:

- событие продуктовой аналитики: ≈ `$0.00005` → **1M событий ≈ $50** сверх free tier
  **[вторичный]**;
- запись session replay: ≈ `$0.005` на первой ступени → **1000 реплеев ≈ $5**; то есть
  **один реплей стоит как 100 событий**;
- логи/трейсы в Grafana Cloud: write `$0.400/GB` + retain `$0.100/GB` → **1 ТБ логов
  ≈ $500/мес** [первичный];
- логи/трейсы в SigNoz Cloud: `$0.3/GB` → **1 ТБ ≈ $300/мес** [первичный].

Отсюда четыре статьи из плана получают числовое подтверждение: сплошная запись реплеев и
неотфильтрованные INFO-логи — две самые дорогие ошибки, и обе решаются сэмплированием по
триггеру, а не сменой вендора.

### 3.4 Точка перехода self-host ↔ SaaS — порядок величины

Считается сравнением цитированных цен выше с ценой ВМ нужного размера. **Цену ВМ этот файл не
фиксирует** (получить её из первоисточника в этой сессии не удалось — сверять у своего
провайдера); зато размер ВМ задан документацией жёстко, и этого хватает для порядка величины.

| Половина | Требование self-host | Когда self-host выигрывает |
| --- | --- | --- |
| **Продуктовая аналитика** | PostHog OSS: одна машина, потолок «a couple 100ks events» **[вторичный]** | **Практически никогда по деньгам.** Потолок self-host (сотни тысяч событий) *ниже* бесплатного облака (1M). Мотив — только резидентность |
| **Ошибки** | Sentry: 4 CPU / 16 ГБ RAM + 16 ГБ swap · GlitchTip: 512 МБ RAM | Sentry self-host против Team-тарифа «$26/mo»: ВМ на 16 ГБ дороже $26 почти у любого провайдера → **self-host Sentry по деньгам не окупается никогда**. GlitchTip на 512 МБ — окупается сразу, но это другой продукт (только ошибки) |
| **Логи/метрики/трейсы** | SigNoz: ≥4 ГБ Docker | Free tier Grafana Cloud = 50 ГБ логов + 50 ГБ трейсов в месяц. Ниже этого self-host — чистый убыток. Выше: 500 ГБ логов в Grafana Cloud ≈ $19 + 500×$0.5 ≈ **$270/мес** против ВМ на 8–16 ГБ — **перелом в районе сотен ГБ в месяц**, то есть ~10× бесплатного тарифа |

> **Вывод, который обязан попасть в ADR-T0005 и в опросник:** для типового проекта из этого
> шаблона **точка перехода лежит выше его объёмов**. Self-host выбирается не по цене, а по
> резидентности — и тогда считается уже не «дешевле ли», а «во что обходится чьё-то внимание».
> Постоянная статья «кто это чинит в субботу» в приведённых суммах не учтена ни разу.

## 4. Грабли

### 4.1 Что ломается при смене вендора

- **Ломается не транспорт, а семантика.** У инженерной половины смена бэкенда решена
  стандартом: OTel Collector переключается конфигурацией экспортёра, приложение не трогают
  [первичный: [OTel — Collector](https://opentelemetry.io/docs/collector/)]. У продуктовой
  половины такого стандарта нет: `posthog.capture("checkout_started", {...})` — имя события и
  набор свойств, а не транспорт. Переехать можно, но **исторические данные не переезжают**, и
  воронка «до и после» разрывается.
- **Отсюда порядок из ADR-T0005:** сначала tracking plan (`docs/ANALYTICS.md`), потом тонкий
  слой над SDK, и только потом вендор. Реестр событий переживает вендора; вызовы SDK в
  обработчиках — нет.
- **Отдельная ловушка PostHog — помодульная тарификация.** Каждый продукт метрится отдельной
  квотой [первичный: posthog.com/pricing], поэтому «переехали на PostHog целиком» на деле
  означает 4–6 независимых счётчиков. Считать бюджет надо по каждому, иначе сюрприз придёт от
  того модуля, о котором не думали (чаще всего — replay).

### 4.2 Где теряется корреляция клиент↔сервер

Четыре типовых обрыва — каждый стоит того, чтобы попасть в скил шага 9:

1. **Заголовок не пробрасывается через CORS.** `traceparent` — кастомный заголовок для
   браузера; без `Access-Control-Allow-Headers` он молча не уходит, и трейс начинается на
   сервере [следует из [W3C Trace Context](https://www.w3.org/TR/trace-context/)].
2. **Продуктовый идентификатор не кладётся в трейс.** `distinct_id` PostHog и `trace_id` OTel
   живут в разных системах; если ни один не записан в атрибуты другого, «на каком шаге
   отвалился и почему» не соединяется — а это главный вопрос плана.
3. **Head sampling выбрасывает именно тот трейс.** Клиент решил «не сэмплировать», сервер
   уважает `trace-flags` — и запрос, за которым пришли, не сохранён
   [первичный: [OTel — Sampling](https://opentelemetry.io/docs/concepts/sampling/)].
4. **Мобильный клиент вне OTel.** Для `react-native` официального OTel-SDK нет (§2.3) —
   корреляция держится на вендорском SDK, и её надо проверять руками, а не считать данной.

### 4.3 Чем реально стоит session replay

- **Деньгами** — дороже всего в пересчёте на единицу: один реплей ≈ 100 событий (§3.3).
  Sentry на free-тарифе даёт «50 replays» — то есть на бесплатном контуре реплеи есть только
  у PostHog (5K) и Clarity.
- **Приватностью.** PostHog маскирует поля ввода по умолчанию («As any input element is highly
  likely to contain sensitive text such as email or password, we mask these by default»), но
  **обычный текст по умолчанию не маскируется**; блокировка элементов — класс `ph-no-capture`,
  замаскированное «is never sent over the network to PostHog»
  [первичный: [PostHog — Replay privacy](https://posthog.com/docs/session-replay/privacy)].
  > То есть **дефолт безопасен только для полей ввода**. Экран с ПДн в обычной вёрстке
  > (профиль, список пациентов, платёжка) пишется целиком, пока не размечен руками. Это и есть
  > вопрос опросника «нужен ли replay при персональных данных на экранах» — и ответ на него
  > почти всегда требует явной разметки, а не отключения инструмента.
- **Бесплатная альтернатива:** Microsoft Clarity — «Free forever... No limits on traffic»,
  SDK для web, Android, iOS, Flutter, React Native
  [первичный: [clarity.microsoft.com](https://clarity.microsoft.com/)]. Цена — данные уезжают
  в облако Microsoft, что закрывает этот путь при требовании резидентности.

### 4.4 Грабля бесплатных тарифов, которую видно только в проде

У Grafana Cloud free tier ограничение «3 active users» — не по объёму данных, а **по людям**.
Проект упирается в него на четвёртом участнике, безотносительно нагрузки
[первичный: [grafana.com/pricing](https://grafana.com/pricing/)]. Такой лимит не виден при
выборе инструмента «по цене за ГБ» и всплывает через полгода.

## 5. Дефолты по стековым профилям `INIT.md` (вход для шага 8)

Каждый профиль называет **два набора**: локальный dev-приёмник и прод-систему.

| Профиль | dev (локально, 0₽, без аккаунта) | prod: продуктовая половина | prod: инженерная половина |
| --- | --- | --- | --- |
| `web-react` | `grafana/otel-lgtm` + события в консоль | PostHog (web SDK: события, воронки, пути, replay) | Sentry (ошибки) + OTel → Grafana Cloud |
| `react-native` | то же | PostHog RN SDK | **Sentry RN SDK** (официального OTel для RN нет — §2.3) |
| `ios-xcode` | Jaeger all-in-one (Swift-OTel стабилен только по трейсам) | PostHog iOS SDK | Sentry Apple SDK |
| `backend-api` | `grafana/otel-lgtm` | PostHog server SDK — **только явные события**, без autocapture | OTel (Stable во всех серверных языках) → Grafana Cloud / SigNoz |
| `cli` | вывод в stderr / файл | **opt-in либо мотивированный отказ в `SPEC.md`** | локальные структурные логи; отправка — только с согласия |
| `desktop` (.NET) | **Aspire dashboard standalone** (OTel .NET Stable по всем трём сигналам) | PostHog .NET SDK | Sentry .NET + OTel |
| `data-ml` | консоль / файл | **opt-in либо мотивированный отказ** | OTel Python (traces/metrics Stable, logs в разработке) |

Для `cli` и `data-ml` навязывание запрещено планом; разведка добавляет к этому техническое
основание — у серверных SDK нет autocapture, то есть «включили и оно само собралось» там не
работает в принципе, каждое событие всё равно пишется руками.

## 6. Развилка резидентности — она меняет всё

Ответ на регуляторный вопрос опросника (шаг 7 плана) — не оттенок, а **другая матрица**.

- **152-ФЗ, ст. 18 ч. 5:** первичные запись, систематизация, накопление, хранение, уточнение и
  извлечение персональных данных граждан РФ выполняются с использованием баз данных,
  **находящихся на территории РФ**; формулировка обновлена ФЗ № 23-ФЗ (опубликован 28.02.2025,
  вступление в силу с 01.07.2025). **[вторичный: сводки
  [КонсультантПлюс](https://www.consultant.ru/law/podborki/lokalizaciya_personalnyh_dannyh/),
  [Б1](https://b1.ru/insights/law-messenger/localization-of-personal-data-of-russian-citizens-6-march-2025/)]**
  — это не юридическая консультация; на проекте под 152-ФЗ формулировку сверяет юрист, а не
  агент.
- **Что из матрицы выживает при требовании «данные не покидают юрисдикцию РФ»:** ни PostHog
  Cloud (US/EU), ни Sentry SaaS, ни Grafana Cloud, ни Clarity. Остаётся self-host: PostHog OSS
  (с его потолком и урезанным набором функций), GlitchTip или Sentry self-host, SigNoz
  self-host. **Free tier перестаёт существовать как опция — и на stage тоже.**
- **GDPR — другой режим:** достаточно EU-региона; PostHog Cloud EU (Франкфурт) и EU-регионы
  остальных SaaS подходят, self-host не обязателен.
- **«Регулирования нет»** — тоже ответ; тогда работает матрица §2 целиком.

> **Поэтому разведка не называет победителя.** Она даёт матрицу, из которой проект выбирает
> после ответа на регуляторный вопрос — это и было решением, зафиксированным в плане при снятии
> open question про юрисдикцию.

## 7. Выводы, которые прямо ложатся в шаги 3–8

1. **ADR-T0005 (схема первична, вендор вторичен) подтверждается:** у продуктовой половины
   стандарта переносимости не существует, историю событий при переезде не забрать. Слой
   абстракции — единственная страховка.
2. **ADR-T0006 (OTel как транспорт) подтверждается сильнее, чем ожидалось:** для инженерной
   половины слой абстракции **не надо писать** — это Collector, и смена бэкенда штатна.
   Корреляционный идентификатор берётся из W3C Trace Context, а не изобретается.
3. **Дефолт «PostHog + Sentry + OTel→Grafana Cloud»** покрывает все семь профилей и целиком
   влезает в бесплатные тарифы на старте. Open question плана «один вендор или связка»
   закрывается в пользу **связки**: у PostHog 50 реплеев Sentry не нужны, а у Sentry 5k
   ошибок — это отдельная дисциплина с лучшим SDK-покрытием.
4. **Dev-профиль: `grafana/otel-lgtm` + события в консоль.** SigNoz local отклонён по весу
   (4 ГБ), Aspire dashboard — дефолт для .NET.
5. **Stage: отдельный проект и ключ** — обосновано поведением обеих систем при исчерпании
   квоты (события молча теряются).
6. **Prod: сэмплирование по триггеру для реплеев, tail-based для трейсов — но не с первого
   дня.** Порог включения записывается в `SPEC.md`; до порога 100% дешевле, чем stateful-узел
   хвостового сэмплирования.
7. **Точка перехода self-host ↔ SaaS — сотни ГБ телеметрии в месяц**, то есть выше объёмов
   типового проекта. Self-host выбирается по резидентности, а не по цене.
8. **Session replay по умолчанию маскирует только поля ввода** — в опросник идёт не галочка
   «нужен ли replay», а вопрос «какие экраны показывают ПДн и кто их разметит».

## 8. Неуверенные места и что осталось за кадром

- **Тарифная лестница PostHog за единицу — [вторичный].** Страница отдаёт цифры JS-калькулятором;
  бесплатные лимиты сверены по первоисточнику, цены сверх — по обзорам 2026. Перед бюджетным
  решением открыть калькулятор на posthog.com.
- **Better Stack и Axiom не сверены** — домены не открылись из этой сессии. В матрице §2.4
  стоят прочерки; если проект их рассматривает, разведку по ним нужно доделать.
- **Цена ВМ не зафиксирована** — арифметика точки перехода (§3.4) даёт порядок величины при
  подставленной цене своего провайдера, а не абсолютное число.
- **Резидентность PostHog EU и возможность миграции US↔EU — [вторичный]:** прямая страница
  `docs/data/eu-us-cloud` вернула 404, сводка собрана из GDPR-документации через поиск.
- **RAM локальных приёмников официально не документирована** ни у Jaeger, ни у otel-lgtm.
  Единственная цитируемая цифра веса — у SigNoz (4 ГБ) и GlitchTip (512 МБ). Требование плана
  «в профиле фиксируется вес» выполнимо только замером на месте — при исполнении шага 8 вес
  otel-lgtm стоит померить (`docker stats`) и записать как измеренный, а не как цитату.
- **152-ФЗ разобран по вторичным источникам** и намеренно не углублялся: это вопрос к юристу
  проекта, а роль шаблона — задать его в опроснике и не дать оставить поле пустым.
- **Не разбирались:** А/Б-платформы и feature flags как отдельный класс (у PostHog входят в
  комплект), RUM/Core Web Vitals, продуктовая аналитика для игровых движков, стоимость
  трафика телеметрии на мобильных тарифах. Кандидаты в `planning/BACKLOG.md`, если понадобятся.
