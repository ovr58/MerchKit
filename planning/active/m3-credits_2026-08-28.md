# Веха M3 — Баллы

Status: DONE (выполнено 2026-08-28)

## Context

M2 закрыта и заархивирована: пользователь регистрируется, подтверждает email, входит,
восстанавливает пароль и выходит; `profiles` живёт под RLS, условие доступа вынесено в единую
SQL-функцию `app.is_owner`. Баланс в профиле есть, но он **всегда 0** — начислить 120 баллов
в обход журнала означало бы написать код, который эта веха сразу выбросит.

M3 — фундамент биллинга. Генерация (M4) тратит баллы, значит списание, возврат и
идемпотентность обязаны существовать и быть проверенными **до** первого потребителя:
спроектированный «на глаз» журнал не переделаешь, когда на нём уже висят реальные операции.
Контракт списания пишется по [V-07](../../docs/VISUALS.md#v-07) и покрывается тестом с
фиктивным потребителем ещё до M4 — это ответ на риск «журнал спроектирован без потребителя».

Границы вехи — [`00_GENERAL_PLAN.md`](../reference/00_GENERAL_PLAN.md) § M3. Цифры утверждены
пользователем 2026-08-27 в [V-09](../../docs/VISUALS.md#v-09) и перенесены в
[`TZ.md`](../../docs/TZ.md) §11: **N = 120**, объект — **50 баллов**, надбавка за тип
«карточка» — **+5**, максимум **1 объект** за генерацию, пакеты **300 / 1 000 / 3 000** баллов
по **390 / 1 090 / 2 030 ₽**. Ничего блокирующего от пользователя не ждём — стартовать можно
сразу. Секция пакетов уже нарисована на артборде `Profile` заходом D1
([V-08](../../docs/VISUALS.md#v-08)), вёрстка идёт по ней.

**Что M2 выяснила про накрутку (2026-08-28, проверено на живом стейдже):** подтверждение email
держит барьер слабее, чем кажется. Плюс-адресация Gmail (`ящик+любое@`) и игнорирование точек
дают одному почтовому ящику неограниченное число «разных» адресов, каждый со своими 120
баллами. Отсюда решение вехи: ключ идемпотентности начисления — **по нормализованному
адресу**, а не по `id` пользователя. Тогда повторное начисление на тот же ящик закрывается
**тем же механизмом, который M3 строит в любом случае** (NFR-03), без отдельной защиты. Чего
это не закрывает: несколько настоящих ящиков и одноразовую почту — против них помогает только
более дорогой признак (телефон, оплата), и это отдельное решение, не довесок к ключу.

## Цель

`ledger` — единственный источник правды о движении баллов. Баланс меняется только Edge
Function с service-role и только в одной транзакции с записью журнала, у каждой записи —
ключ идемпотентности. Начисление 120 по подтверждению email, пакеты пополнения с мгновенным
зачислением, списание и возврат с проверенным контрактом под будущего потребителя.

## Границы

**Входит:** таблица `ledger` + RLS в той же миграции · единственная точка изменения баланса
(транзакция «журнал + баланс») · ключ идемпотентности (NFR-03) · начисление N по
подтверждению email (FR-19) с ключом по нормализованному адресу · баланс в профиле (FR-22) ·
пакеты пополнения без оплаты (FR-23, US-05) · модуль `pricing` — одинаковый расчёт на клиенте
и на сервере, источник правды серверный · контракт списания/возврата по V-07 с тестом на
фиктивном потребителе · удаление аккаунта (152-ФЗ) вместе с решением о судьбе журнала.

**Не входит:** эквайринг ([B4](../BACKLOG.md)) — пакеты зачисляются без оплаты сознательно ·
сама генерация и её экраны (M4) · каталог (M4) · защита от нескольких настоящих ящиков и
одноразовой почты: это более дорогой признак и отдельное решение.

## Шаги

### 0. Развилки, которые решаются до кода

- [x] Ветка `claude/m3-credits` от `main` (доверенная полоса, [ADR-0002](../../docs/adr/0002-trust-lane-by-model-not-host.md)).
      Пуш — по отдельной команде пользователя.
- [x] **Где ловится «email подтверждён» → триггер БД на `auth.users`.**
      Auth Hook отпадает фактически: у Supabase нет хука «пользователь подтвердил email» —
      есть `custom-access-token`, `send-email`, `mfa-verification-attempt`,
      `password-verification-attempt`, и ни один не означает подтверждение. Edge Function,
      вызываемая клиентом, отпадает по критерию: начисление обязано пережить то, что
      пользователь закроет вкладку сразу после перехода по ссылке.
      Остаётся `after update of email_confirmed_at on auth.users` при переходе NULL → not
      null — тот же механизм, которым M2 заводит профиль (`on_auth_user_created`).
      Начисление идёт **внутри транзакции подтверждения**: подтвердилось — начислено.
      **ADR не нужен — откат стоит одной миграции `drop trigger`.**
      Побочное следствие: точкой изменения баланса становится не только Edge Function с
      service-role, но и `security definer`-функция БД. Инвариант «клиент не двигает баланс»
      это не ломает, но формулировку `SPEC.md` §3 пришлось уточнить в том же изменении.
- [x] **Судьба записей `ledger` при удалении аккаунта → обезличивание на месте.**
      `user_id uuid references auth.users (id) on delete set null` (колонка nullable):
      строка журнала переживает удаление без владельца, RLS её больше никому не показывает.
      Ключ идемпотентности остаётся — а значит, ключ **не может содержать сам адрес**:
      это была бы персональная данная, пережившая отзыв согласия. Отсюда
      `signup:<sha256(нормализованный адрес)>`, `sha256` — встроенная функция Postgres.
      Следствие принято сознательно: удалил аккаунт → зарегистрировался тем же ящиком →
      120 баллов второй раз не начисляются. Решение и его цена — [ADR-0009](../../docs/adr/0009-ledger-survives-account-deletion.md).

### 1. Миграция `ledger` — журнал и единственная точка изменения баланса

- [x] Таблица `public.ledger`: владелец, знаковая дельта, вид операции, ключ идемпотентности,
      контекст операции, момент. Внешний ключ — `on delete set null` по решению шага 0.
      **Сверх списка добавлена колонка `balance_after`** — баланс после операции. Колонка
      «Баланс» в истории обязана оставаться верной при любой выборке, а досчитать её на
      клиенте можно только по всему журналу целиком.
- [x] **Уникальный индекс по ключу идемпотентности** — идемпотентность держит БД, а не
      аккуратность вызывающего кода (NFR-03).
- [x] RLS **в этой же миграции** (сквозное правило генплана): `select` своих записей через
      `app.is_owner`, политик на запись нет намеренно — service-role RLS обходит. Гранты
      повторяют то же намерение: `revoke all`, `grant select to authenticated`.
- [x] SQL-функция «применить операцию» — `public.apply_credit_operation`: в одной транзакции пишет строку журнала и двигает
      `profiles.balance`. Повторный ключ — не ошибка, а no-op с текущим балансом. Уход в
      минус невозможен: `check (balance >= 0)` на `profiles` стоит с M2.
- [x] Комментарии на таблицу и колонки — как в `supabase/migrations/20260828000000_profiles.sql`;
      комментарий M2 «на M2 всегда 0» устарел этой вехой, обновить.

### 2. Начисление N по подтверждению email (FR-19)

- [x] Нормализация адреса: нижний регистр; для Gmail/Googlemail — убрать точки в локальной
      части и всё начиная с `+`. Чистая функция с тестом на наборе кейсов, включая не-Gmail
      (там точки значимы и вырезать их нельзя).
      **Написана на SQL (`app.normalize_email`), а не на TypeScript:** начисление живёт в
      триггере БД, и копия на TS не имела бы ни одного потребителя — только шанс разойтись
      с оригиналом. Тест — в pgTAP, на том же наборе кейсов.
- [x] Ключ начисления — `signup:<sha256(нормализованный адрес)>`: сам адрес в ключ не
      попадает, иначе он пережил бы удаление аккаунта (ADR-0009). Само начисление 120 идёт через
      функцию из шага 1, только серверной логикой.
- [x] Механизм срабатывания — триггер `on_auth_user_confirmed` по решению шага 0.
      **Добавлен второй путь:** `on_auth_user_created_confirmed` на INSERT — администратор
      заводит пользователя сразу подтверждённым через Studio, и UPDATE тогда не случается.
      **Плюс разовая догонка** тех, кто подтвердил email до этой миграции: иначе они
      остались бы с нулём навсегда. Повтор безопасен — ключ тот же.

### 3. Модуль `pricing` — одна цена, два места

- [x] Расчёт: 50 баллов за объект, +5 за тип «карточка», максимум 1 объект за генерацию
      (политика продаж, не техническое ограничение — [`TZ.md`](../../docs/TZ.md) §11).
- [x] Один и тот же расчёт на клиенте (показ) и на сервере (списание). Клиентская цена —
      справочная; расхождение — ошибка, а не «клиент прав» ([`SPEC.md`](../../docs/SPEC.md) §3).
      **Реализация буквально одна:** `supabase/functions/_shared/pricing.ts`, клиент
      подключает её алиасом `@shared`. Файл лежит внутри `supabase/functions/`, потому что
      обратное направление (файл в `src/`, импорт из Deno) в облако может не доехать.
- [x] Тест на общем наборе кейсов. **Сверять две стороны нечего** — реализация одна, и
      расхождение стало структурно невозможным, а не проверяемым. Тест закрепляет сами
      числа из [`TZ.md`](../../docs/TZ.md) §11.

### 4. Пакеты пополнения (FR-23, US-05)

Ветка `claude/m3-credits`, 2026-08-28. Не отправлена и не задеплоена — по канону это отдельная
команда пользователя.

**Миграции** (`supabase/migrations/`): `..120000_ledger.sql` — таблица, уникальный ключ

**Клиент:** модуль `billing` с публичным интерфейсом (баланс, пакеты, история), общий с

(удаление аккаунта) · заметка о расхождении с артбордом в `VISUALS.md` V-08 · `CONTEXT.md`
и `GLOSSARY.md` (идемпотентность, плюс-адресация).

**Что нашлось по дороге и было починено:**

- `revoke all on function … from public` **не закрывает функцию** от `authenticated`: в схеме
  `public` Supabase раздаёт `execute` прямыми грантами ролям через `alter default privileges`.
  До правки любой вошедший мог вызвать `apply_credit_operation` и начислить себе баллов.
  Нашёл RLS-тест — до правки он падал тремя проверками из двенадцати.
- Тест «строка журнала пережила удаление» сначала считал **все** обезличенные строки в базе и
  падал после прогона `test:billing`. Переписан на проверку своей строки по ключу — ровно та
  хрупкость, о которой предупреждает тест M2.
- Первая версия сквозной проверки удаления не могла упасть в принципе (`length >= 0`) и
  проверяла аккаунт **без** записей в журнале. Переписана на счёт «до и после».
- **Двойной клик по пакету зачислял его дважды.** Нашла проверка Playwright: два клика с
  разницей 122 мс дали баланс 2120 вместо 1120 и две строки в журнале. Юнит-тест это
  пропустил, потому что проверял ключ попытки при отказе, а щель была при **успехе**: клиент
  ротирует ключ после зачисления, и второй клик уходит со своим ключом — для сервера он
  неотличим от новой покупки. Чинить на клиенте бессмысленно: любая схема, где клик может
  сменить ключ, ломается вторым кликом. Правка серверная — окно в 10 секунд на пару
  «пользователь + пакет» внутри `topup_balance`; второй клик отвечает текущим балансом, а не
  ошибкой, потому что для человека двойной клик обязан выглядеть как одна удачная покупка.
- **403 в консоли после удаления аккаунта — разобрано, но НЕ убрано.** Первая правка
  (`signOut({ scope: 'local' })`) была сделана по неверному предположению, что локальный выход
  не ходит в сеть; повторная проверка Playwright показала тот же 403, и исходник SDK это
  подтвердил: `GoTrueClient._signOut` зовёт `/auth/v1/logout` при любом scope, а 403 сам же
  перечисляет среди игнорируемых — локальная сессия чистится в любом случае. `scope: 'local'`
  оставлен как верное намерение, комментарий приведён к факту. Убрать строку в консоли можно
  было бы только выходом ДО удаления, но тогда неудачное удаление стоило бы человеку
  повторного входа: косметика такой цены не стоит.

**Проверено:** `npm run test` (31) · `npm run lint` · `npm run build` · `npm run test:db` (37) ·
`npm run test:flow` (16) · `npm run test:billing` (14, новый) — всё зелёное на локальном
