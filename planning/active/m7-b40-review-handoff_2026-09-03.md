## Полоса доверия — прочитать первым делом

Работа B4.0 сделана **Opus 5** (трейлеры `Co-Authored-By` на всех коммитах диапазона). По
ADR-0002 это доверенная полоса, где self-review разрешён. **Но ветка называется
`feature/m7-phase-b`** — имя консервативной полосы, и на ней лежит более ранняя работа фазы B.
Пользователь запросил review-handoff явно, поэтому self-approve не делался.

Ревьюеру решить: считать ли диапазон доверенной полосой по трейлерам или консервативной по
имени ветки. Прецедент разбора именно этого расхождения — [M5](../archive/plans/m5-review-handoff_2026-08-30.md).

## Что сделано и зачем

Шаг **B4.0** плана [`card-assembly-pipeline_2026-08-31.md`](card-assembly-pipeline_2026-08-31.md) —
бесплатный замер-гейт перед B4. Три задачи одной оснасткой, как требовало уточнение плана от
2026-09-03:

1. **Замер раннера выреза** (требование [ADR-0014](../../docs/adr/0014-cutout-runner-onnx-behind-interface.md), пункт 3): влезает ли ONNX в изолят, то же в браузере, лицензии по первоисточникам.
2. **Долг ревью B6 №1** — эффект явного `free()` у объектов `resvg`, который в Node не измерялся.
3. **Долг ревью B6 №2** — «внешняя память до 81 МБ» из таблицы B0.1: пик одной сборки или накопление.

Оснастка коммитится, а не пишется разово, потому что смоук B0.1 не сохранился и переспросить
его собственные числа было нечем.

## На что смотреть в первую очередь

1. **`render.ts` — единственная правка продуктового кода.** Экспорт `rendererFonts()` добавлен
   не ради удобства: `initWasm` у `@resvg/resvg-wasm` глобален для модуля, специфик импорта у
   `render.ts` и `card-bench` один, и второй загрузчик вызвал бы `initWasm` на уже поднятом
   экземпляре. Проверить, что рассуждение верно и что экспорт не расширяет поверхность модуля
   сверх нужного.
2. **`card-bench` не должен уехать в стейдж.** Защит две: проверка `isServiceRoleCaller` первым
   делом и отсутствие функции в `config.toml`. Деплой в проекте — только по явной команде
   пользователя. Ревьюеру оценить, достаточно ли этого или нужна явная запись в конфиге.
3. **Бакет `card-bench` заводится драйвером на лету**, миграцией не описан
   (`bench.mts`, `ensureBucket`). Обоснование: модель не лезет в `card-render-assets` (потолок
   5 МБ и белый список типов, заданные миграцией `20260901130000`), а менять продуктовую схему
   до выбора модели — значит отвечать миграцией на незаданный вопрос. Бакет живёт только на
   локальном стенде и уносится `db reset`. Проверить, что это не создаёт расхождения схемы.
4. **Выводы против чисел.** Все числа воспроизводимы командами ниже. Особенно проверить вывод
   «`free()` работает»: он держится на том, что внешняя память выходит на плато при
   освобождении и растёт без него, — а не на одном прогоне.

### Про три падения pgTAP — прочитать, прежде чем считать ветку красной

Падают `card_layouts` #14 и `generation_costs` #5, #8. **Причина — не код ветки, а остатки
данных на локальном стенде.** Доказательство арифметикой, без сброса базы:

| Тест | have | want | Δ |
| --- | --- | --- | --- |
| `generation_costs` #5 «И ничего не пишет» | 6 | 2 | 4 |
| `generation_costs` #8 каскад себестоимости | 4 | 0 | 4 |
| `card_layouts` #14 каскад снимка карточки | 1 | 0 | 1 |

В базе лежат `generation_costs` — 4 строки, `generation_cards` — 1 строка, **все датированы
2026-09-02**, то есть появились до этой работы (`select count(*), max(created_at) …`).
Каждая дельта объясняется точно.

**Корневая причина — устройство самих тестов:** они считают строки глобально
(`select count(*)::int from public.generation_costs`, `generation_costs.test.sql:69`), а не в
границах своих фикстур, поэтому зелены только на свежесброшенной базе. Это находка, но
принадлежит она шагам B0/B2 и вехе M5, а не B4.0, и правкой в этой ветке я её не трогал —
1 баг = 1 правка в 1 месте.

**Ревьюеру:** подтвердить на чистой базе (`supabase db reset`, затем `npm run cards:layouts push`,
`npm run cards:assets push`, `npm run cards:render-assets`, затем `npm run test:db`) и решить,
чинить ли тесты отдельным изменением.

## Как воспроизвести числа замера

```
npx supabase functions serve                          в отдельном терминале

npm run cards:bench assemble                          сборка 34 макетов в двух размерах
npm run cards:bench free acupressure-mat-callouts --rounds 20 --repeat 40
npm run cards:cutout licenses                         лицензии по первоисточникам
npm run cards:cutout fetch u2netp                     ~4,4 МБ
npm run cards:bench cutout u2netp --rounds 4          вырез в изоляте
npm run cards:cutout node u2netp                      он же без супервизора
```

Полный прогон `cards:cutout fetch` без аргументов качает ~600 МБ чужих весов — для проверки
выводов достаточно `u2netp`.

## Выводы, которые ревью должно подтвердить или опровергнуть

1. **`free()` у `resvg` работает и нужен.** С освобождением внешняя память упирается в плато
   (10,9 МБ) независимо от числа прогонов; без него растёт ~2,4 МБ за прогон и плато не находит
   (3 прогона → 16,4 МБ, 6 → 22,5 МБ). Цена — около 10% времени обмера.
2. **«81 МБ» — пик одной сборки, а не накопление.** Пик за ряд 40,2 МБ при наибольшем приросте
   за один прогон 37,3 МБ на том же макете; повторные сборки одного макета в одном изоляте
   держат уровень.
3. **Бюджет процессорного времени супервизора — на воркер, а не на запрос.** Изолят
   переподнимается каждые два-три полноразмерных прогона. Отказ приходит двумя кодами: `503`
   с пустым телом и `546` с телом `WORKER_LIMIT`.
4. **В изолят не помещается ни сборка в размере профиля площадки, ни инференс.** Сборка —
   19–21 макет из 34. Инференс не завершился ни разу; в Node на том же wasm самый лёгкий
   кандидат просит 2001 мс при жёстком пределе изолята около двух секунд на весь запрос.
5. **Лицензии:** быстрейший кандидат `u2netp` — тот, чьи веса лицензия не покрывает
   (README отправляет к авторам письмом); `bria-rmbg` прямо некоммерческая; чистые `ormbg`
   (Apache-2.0) и `birefnet` (MIT) — самые тяжёлые, причём `ormbg` на товаре даёт кашу.

## Долги ветки, найденные при подготовке хендоффа

- **Восемь коммитов `dev-tooling` (`09729b1`…`09b9c2d`) не несут трейлера `Co-Authored-By`.**
  Конвенция проекта требует трейлер на каждом коммите; именно по трейлерам в M5 нашли пробел
  полосы доверия. Историю не переписываем — фиксирую здесь.
- **`b0f9587 fix(auth)` и те же восемь коммитов `dev-tooling` ревью не проходили** ни разу:
  в плане они не упомянуты, в разборах B0–B2 и B3/B6 их нет.
- **Правки по ревью B6 (`bfde400`) ревьюером не перепроверялись** — по прецеденту M5 это
  отдельный шаг.
