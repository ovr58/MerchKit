# ADR-0006: Supabase — единственный бэкенд; изоляция данных на RLS, баланс — только сервером

- **Status:** Accepted
- **Date:** 2026-08-26
- **Related:** `docs/SPEC.md` §1–§4 · `docs/TZ.md` §8, NFR-03, NFR-04, NFR-05 ·
  [V-03](../VISUALS.md#v-03), [V-04](../VISUALS.md#v-04)

## Context

Стек задан заказчиком: React.js + Supabase (`TZ.md` §8). Само по себе это ещё не архитектура —
оставался открытым вопрос, появляется ли рядом с Supabase собственный бэкенд-сервис, и где
проходит граница доверия к браузеру.

Обстоятельства проекта:

- серверной логики мало — по сути четыре операции: запуск генерации, фоновая обработка,
  пополнение, начисление при регистрации;
- у продукта есть **внутренняя валюта** (баллы), а значит есть прямой мотив её подделать;
- ключ AI-провайдера нельзя отдавать браузеру;
- генерация идёт десятки секунд, то есть не укладывается в обычный запрос-ответ.

Ловушка этого стека в том, что Supabase поощряет ходить в базу прямо из браузера с
`anon`-ключом. Это удобно и совершенно нормально для чтения — и катастрофично, если так же
обращаться с балансом: `anon`-ключ публичен by design, он лежит в JS-бандле, и единственное,
что реально защищает данные, — политики RLS.

## Decision

**Собственного бэкенд-сервиса нет. Supabase закрывает auth, БД, файлы, realtime и серверную
логику. Граница доверия проходит по трём правилам.**

1. **Чтение своих данных — напрямую из браузера**, под защитой RLS по `auth.uid()`. RLS
   включается **в той же миграции, где создаётся таблица**, — не «потом».

2. **Всё, что меняет деньги или зовёт провайдера, — только Edge Function** с service-role:
   запуск генерации, списание, возврат, пополнение, начисление при регистрации. Клиенту
   таблицы `profiles.balance` и `ledger` доступны **только на чтение**.

3. **Баланс — производная от журнала.** `profiles.balance` меняется исключительно в одной
   транзакции с записью в `ledger`, и каждая запись журнала несёт ключ идемпотентности.
   Повторная доставка одного события не двигает баланс дважды (NFR-03).

Генерация — **асинхронная**: заявка возвращает `generationId`, статус живёт в БД, клиент
подписан на его изменения через Realtime ([V-07](../VISUALS.md#v-07)). Это же снимает
NFR-02: перезагрузка страницы не теряет результат.

Пополнение проводится через тот же `ledger`, что и списание, — хотя эквайринга в этой версии
нет (`TZ.md` §3) и баллы зачисляются мгновенно.

## Consequences

**Обязаны:**

- каждая новая пользовательская таблица создаётся вместе с RLS-политикой и тестом «чужой
  `id` → отказ» (`SPEC.md` §7);
- любое изменение баланса проходит через `ledger` с ключом идемпотентности;
- секреты (`SERVICE_ROLE_KEY`, ключ провайдера) живут только в секретах Edge Functions.

**Чего нельзя:**

- писать в баланс из клиента — даже «временно, потом перенесём»;
- считать `anon`-ключ секретом и полагаться на него как на защиту;
- заводить второй источник правды о балансе (кэш, поле в другой таблице, значение в UI).

**Цена решения:**

- сложная логика на Deno в Edge Functions менее удобна, чем в полноценном бэкенде, и при
  сильном росте продукта может упереться в лимиты — тогда потребуется новый ADR о выносе
  фоновой обработки;
- привязка к Supabase дорога к откату: RLS-политики, Edge Functions и Storage — не
  переносимый Postgres. Это принято как следствие ограничения ТЗ, а не как свободный выбор.

**Что становится дешевле:** добавление реального эквайринга позже не трогает баланс — платёж
лишь становится ещё одним источником записи в `ledger`.
