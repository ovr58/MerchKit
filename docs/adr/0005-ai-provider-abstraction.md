# ADR-0005: AI-провайдер прячется за абстракцией, выбор откладывается

- **Status:** Accepted
- **Date:** 2026-08-26
- **Related:** `docs/SPEC.md` §2, §3, §5 · `docs/TZ.md` §8, §11 · [V-03](../VISUALS.md#v-03)

## Context

Merch Kit целиком построен вокруг генеративного AI: провайдер закрывает четыре разные
операции — распознавание товара и категории по фото (FR-03, FR-04), генерацию изображений в
выбранном сценарии (FR-14), тексты карточки (FR-07) и название генерации (FR-16).

На интейке провайдер **сознательно не выбран**: пользователь отложил решение. При этом
качество продукта упирается ровно в одну характеристику провайдера — способность сохранить
предмет с загруженного фото узнаваемым. Проверить это можно только опытом на реальных фото
товаров, а не по документации, и рынок таких моделей меняется быстрее, чем пишется
приложение.

Силы, между которыми выбор:

- писать код под конкретного провайдера **сейчас** — быстрее, но привязывает продукт к
  вендору, которого ещё не выбирали, и делает сравнение вариантов дорогим;
- ждать выбора провайдера — блокирует всю остальную разработку, хотя она от провайдера
  почти не зависит.

Дополнительное ограничение: ключ провайдера нельзя отдавать браузеру (`TZ.md` §8), поэтому
любой вызов и так проходит через серверный слой — место для абстракции уже существует.

## Decision

**Провайдер скрыт за интерфейсом `ai-provider` в Supabase Edge Functions. Остальной код —
и клиентский, и серверный — не знает имени провайдера.**

Интерфейс задаёт **четыре независимые операции**, а не одну «сходить в AI»:

- `recognize(photo)` → наименование товара + категория из перечня `TZ.md` §5.1;
- `generateImages(params)` → N изображений по сценарию показа и пожеланиям;
- `composeCard(params)` → заголовок и описание для типа «карточка»;
- `nameGeneration(params)` → название генерации для каталога.

Следствия деления:

- операции можно закрыть **разными** провайдерами (распознавание и тексты — дешёвой
  мультимодальной моделью, изображения — специализированной);
- для окружения `local` реализуется **заглушка**, возвращающая фиксированные изображения,
  чтобы разработка не жгла бюджет на каждом прогоне (`SPEC.md` §6);
- сравнить двух кандидатов = написать вторую реализацию интерфейса, а не переписать приложение.

Промпты сценариев показа при этом **не живут в коде** — они данные в таблице `presets`
([V-04](../VISUALS.md#v-04)), потому что их 24 и они правятся без релиза.

Каждый вызов провайдера пишет в лог свою длительность и себестоимость рядом с `generationId`
(`SPEC.md` §8) — без этого нельзя проверить, что прайс в баллах не убыточен (`TZ.md` §10).

## Consequences

**Обязаны:**

- никогда не вызывать провайдера из браузера и не импортировать его SDK в клиентский код;
- добавляя новую AI-возможность, расширять интерфейс, а не звать провайдера мимо него;
- держать заглушку провайдера рабочей — она часть тестового контура (`SPEC.md` §7).

**Чего нельзя:** протаскивать специфичные для вендора поля (форматы ответа, названия моделей,
коды ошибок) в типы, которые видит UI. Наружу интерфейса выходят только доменные понятия
Merch Kit.

**Цена решения:** один лишний слой и невозможность использовать уникальные фичи конкретного
провайдера «по-быстрому», не расширив интерфейс. Принимается сознательно.

**Что закрывается позже:** сам выбор провайдера — отдельный ADR со `Status: Accepted`,
после практической проверки кандидатов на реальных фото товаров. До тех пор в `SPEC.md` §2
строка провайдера остаётся незаполненной, и это не считается пробелом в спецификации.
