# ADR-0009: Журнал операций переживает удаление аккаунта обезличенным

- **Status:** Accepted
- **Date:** 2026-08-28
- **Related:** [`SPEC.md`](../SPEC.md) §4 · [`TZ.md`](../TZ.md) NFR-03, NFR-06 ·
  [`CONTEXT.md`](../../CONTEXT.md) «Журнал операций» · [ADR-0006](0006-supabase-as-backend.md) ·
  план вехи M3

## Context

`profiles` каскадится от `auth.users`: удалили пользователя — профиль исчез вместе с ним.
Для баланса это правильно, для **журнала операций** — нет. `ledger` заводится вехой M3 как
единственный источник правды о движении баллов: по нему сходится баланс, по нему разбирается
спор «за что списали», по нему считается, сколько сервис реально раздал бесплатных баллов.
Учётный регистр, из которого задним числом исчезают строки, перестаёт быть учётным регистром.

С другой стороны, по 152-ФЗ у пользователя есть право отозвать согласие на обработку
персональных данных, и веха M3 заводит кнопку удаления аккаунта именно под это. Значит,
хранить в журнале то, что указывает на человека, после удаления нельзя.

Отдельно давит третье обстоятельство. Ключ идемпотентности начисления стартовых баллов —
**по нормализованному почтовому адресу**, а не по `id` пользователя: плюс-адресация Gmail
даёт одному ящику неограниченное число «разных» адресов, каждый со своими 120 баллами
(проверено на живом стейдже 2026-08-28). Если журнал переживает удаление, ключ переживает его
тоже — иначе «удалить аккаунт и зарегистрироваться заново» становится способом получать
стартовые баллы бесконечно, и удаление превращается в дыру шире той, которую ключ закрывает.

Рассмотренные варианты:

1. **Каскадить журнал вместе с профилем.** Дёшево, но убивает учётный регистр и открывает
   накрутку через «удалить и зарегистрироваться».
2. **Хранить журнал отдельной таблицей без связи с пользователем.** Даёт то же, что вариант 3,
   но ценой второй таблицы и ручной поддержки связи там, где её умеет держать внешний ключ.
3. **Обезличивать строку на месте.**

## Decision

**Строка `ledger` переживает удаление аккаунта обезличенной, ключ идемпотентности остаётся.**

- `user_id uuid references auth.users (id) on delete set null`, колонка nullable. Удаление
  пользователя не трогает строку журнала — только обнуляет владельца.
- Обезличенная строка невидима вообще никому, кроме service-role: RLS-политика построена на
  `app.is_owner(user_id)`, а `auth.uid() = null` не истинно ни для кого.
- **Ключ идемпотентности не содержит адрес** — только его отпечаток:
  `signup:<sha256(нормализованный адрес)>`. Иначе после удаления аккаунта в базе остался бы
  сам email, то есть ровно та персональная данная, ради удаления которой всё затевалось.
  `sha256` — встроенная функция Postgres, отдельного расширения не требует.

## Consequences

**Обязаны:**

- Помнить, что удаление аккаунта **не возвращает право на стартовые баллы**. Зарегистрировался
  тем же ящиком после удаления — 120 баллов не начисляются. Это не дефект, а цена решения;
  формулировка в интерфейсе удаления обязана об этом предупреждать.
- Держать `user_id` nullable во всех запросах к журналу: строка без владельца — штатное
  состояние, а не повреждённые данные.

**Теряем:**

- Возможность разобрать претензию удалённого пользователя по существу: строки в журнале есть,
  но чьи они — уже не восстановить. Это осознанная плата за отзыв согласия.
- Строгую анонимность: `sha256` от адреса — псевдонимизация, а не обезличивание. Адрес из
  отпечатка не читается, но проверить гипотезу «был ли зарегистрирован вот этот ящик»
  перебором по словарю можно. Убрать и это — значит выкинуть ключ, то есть вернуть накрутку.

**Не меняется:**

- Баланс остаётся производной величиной в `profiles` и по-прежнему двигается только вместе с
  записью журнала в одной транзакции (NFR-03, NFR-05).
- Защита от нескольких настоящих ящиков и одноразовой почты этим решением не закрывается —
  против неё помогает только более дорогой признак (телефон, оплата), и это отдельное решение.
