# ADR-T0006: OpenTelemetry как транспорт инженерной половины и сквозной корреляционный идентификатор

- **Status:** Accepted
- **Date:** 2026-09-04
- **Related:** ADR-T0005 (схема событий первична); `planning/reference/ANALYTICS_RESEARCH.md`
  §1, §2.3, §4.2; `planning/archive/plans/analytics-observability-by-default_2026-09-04.md` шаг 3

## Context

Аналитика и наблюдаемость — **две подсистемы с разными потребителями**: продуктовая отвечает
«кто пришёл, что делал, где отвалился» (потребитель — владелец продукта), инженерная — «что
сломалось, где медленно, почему» (потребитель — разработчик). По отдельности каждая половина
отвечает на свой вопрос и **не отвечает на главный**: видно, что пользователи отваливаются на
шаге 3, но не видно, почему; видно ошибку в логе, но не видно её цены для продукта.

Склейка половин — **общий корреляционный идентификатор**, проброшенный от клика в UI до строки
лога на сервере. Без него «затык потока» диагностировать нельзя: два хранилища данных, которые
невозможно соединить запросом, — это не система наблюдаемости, а два несвязанных дашборда.

Что дала разведка:

- **Идентификатор не надо изобретать.** W3C Trace Context — **W3C Recommendation от
  2021-11-23**, задаёт HTTP-заголовки `traceparent` / `tracestate` и формат
  `version-trace-id-parent-id-trace-flags`. Это норма, а не соглашение одного вендора.
- **Транспорт не надо писать.** OpenTelemetry Collector — «a vendor-agnostic way to receive,
  process and export telemetry data»; смена бэкенда наблюдаемости — правка конфигурации
  экспортёра **без изменения кода приложения**. То есть для инженерной половины слой абстракции
  из ADR-T0005 уже существует как индустриальный стандарт, и писать свой — дублирование.
- **Зрелость SDK неравномерна и это надо знать заранее:** .NET и Java — traces/metrics/logs все
  Stable; JavaScript и Python — traces/metrics Stable, logs в разработке; **Swift — Stable
  только traces**; **официального OTel-SDK для React Native не существует вовсе** — там
  доступны только вендорские дистрибутивы и community-библиотеки.

Варианты, которые рассматривались:

1. **Логировать как раньше, корреляцию не вводить.** Отвергнут: это статус-кво, при котором
   главный вопрос плана («на каком шаге отваливаются и что делали перед этим») не имеет ответа
   в принципе, сколько бы логов ни собрали.
2. **Свой корреляционный заголовок (`X-Request-Id` и подобное).** Отвергнут: работает ровно до
   первой внешней системы. Любой прокси, API-шлюз, брокер очередей и вендорский SDK умеют
   `traceparent` и не умеют самодельный заголовок — цепочка рвётся на первом же чужом узле.
3. **Прямая интеграция SDK бэкенда наблюдаемости (агент вендора вместо OTel).** Отвергнут по
   той же логике, что и в ADR-T0005: даёт ту же сшивку с вендором, но без выигрыша — стандарт
   уже существует и покрывает те же сигналы.
4. **OTel как транспорт + `traceparent` как идентификатор.** Принят.

**Почему дорого откатить.** Корреляционный идентификатор — сквозной по определению: он
пробрасывается через клиент, шлюз, все сервисы, очереди и фоновые задачи. Ввести его позже —
значит пройти по всем этим точкам ещё раз, причём в уже работающей системе. Хуже того, отсутствие
корреляции обнаруживается **в момент инцидента**, когда цепочку надо восстановить задним числом,
а данных для этого не собрано и собрать их ретроспективно невозможно.

## Decision

**Инженерная половина строится на OpenTelemetry; корреляция — на W3C Trace Context.**

- **Транспорт логов, метрик и трейсов — OTel SDK + Collector.** Приложение отправляет сигналы в
  Collector; выбор и смена бэкенда (Grafana Cloud, SigNoz, self-host) — конфигурация экспортёра,
  а не правка кода.
- **Свой слой абстракции над OTel не пишется.** Требование ADR-T0005 «не вызывать SDK вендора
  напрямую» на инженерную половину **не распространяется**: OTel и есть вендор-нейтральный
  интерфейс, обёртка над ним — дублирование (правило `ponytail`: stdlib/native прежде своего).
- **Корреляционный идентификатор — `traceparent` по W3C Trace Context.** Собственные заголовки
  для сквозной корреляции не заводятся. `trace-id` проходит от клиентского запроса до строки
  лога на сервере.
- **Две половины сшиваются явной записью идентификаторов друг друга.** Продуктовый
  идентификатор (`distinct_id` / `session_id`) записывается в атрибуты трейса, а `trace_id` —
  в свойства продуктового события. Односторонней связи недостаточно: запрос идёт с обеих сторон
  («почему отвалился этот пользователь» и «кого задела эта ошибка»).
- **Логи — структурные и с `trace_id`.** Правило канона «логировать только через логгер
  проекта» дополняется: запись без корреляционного идентификатора не диагностична и считается
  незавершённым логированием.
- **Одно инструментирование на все окружения, разные приёмники.** Код сбора одинаков в
  local/stage/prod; различаются экспортёр, sampling, retention и режим данных. Разные системы на
  разных окружениях запрещены: тогда инструментирование впервые исполняется в проде, то есть
  непроверенным.
- **Sampling: 100% по умолчанию, tail-based — по порогу.** Head-based sampling выбрасывает
  случайное и не гарантирует сохранение ошибочных трейсов; tail-based сохраняет медленные и
  ошибочные, но требует отдельного stateful-компонента со своей стоимостью. Поэтому порог
  перехода записывается в `docs/SPEC.md`, а не вводится с первого дня.
- **Идентификаторы — в трейсы и события, не в метки метрик.** `user_id` меткой метрики даёт
  взрыв кардинальности; в метках допустимы только ограниченные множества.
- **Там, где официального OTel-SDK нет, это записывается явно.** Для `react-native` инженерная
  половина на клиенте берётся у вендора (Sentry RN SDK), и корреляция клиент↔сервер проверяется
  вручную. Обещание «один OTel везде» в таком профиле давать нельзя.

## Consequences

**Что теперь обязаны:**

- Пробрасывать `traceparent` через все границы: клиент → шлюз → сервисы → очереди → фоновые
  задачи. Разрыв цепочки — дефект, а не «неохваченный участок».
- Для браузерного клиента — разрешать `traceparent` в CORS (`Access-Control-Allow-Headers`),
  иначе заголовок молча не уходит и трейс начинается на сервере.
- Записывать `trace_id` в структурные логи и продуктовый идентификатор в атрибуты трейса.
- Проверять корреляцию как поведение: факт «трейс собран сквозным от клика до строки лога»
  подтверждается **в dev**, а не выясняется в проде во время инцидента.
- Фиксировать в `docs/SPEC.md` выбранный бэкенд, sampling и порог включения tail-based.

**Чего теперь нельзя:**

- Заводить собственный сквозной корреляционный заголовок вместо `traceparent`.
- Писать обёртку над OTel «чтобы можно было сменить» — сменяемость обеспечивает Collector.
- Ставить `user_id` и другие неограниченные идентификаторы метками метрик.
- Разворачивать разные системы наблюдаемости на dev и prod.

**Цена:** OTel — не бесплатная в освоении технология: конфигурация Collector, понимание
разницы сигналов и sampling требуют времени, а зрелость SDK по языкам неравномерна (для Swift
стабильны только трейсы, для React Native официального SDK нет). Принято сознательно:
альтернатива — сшивка с вендором без выигрыша в простоте и невосстановимое отсутствие
корреляции в момент инцидента.

**Границы решения:** ADR не выбирает бэкенд наблюдаемости — он делает выбор сменяемым; конкретный
бэкенд называется в `docs/SPEC.md`. Он не распространяется на продуктовую половину: там
переносимого стандарта нет и действует ADR-T0005 со своим слоем абстракции. И он не обязывает
включать телеметрию в профилях `cli` и `data-ml` — там сбор остаётся opt-in либо мотивированно
отклонённым.
