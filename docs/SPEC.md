## 1. Архитектура

**Общая идея решения.** Классический BaaS-расклад без собственного бэкенд-сервиса: React-SPA
разговаривает напрямую с Supabase (auth, БД, файлы, realtime), а всё, что нельзя доверить
браузеру — вызов AI-провайдера, списание баллов, начисление пакетов, — живёт в Supabase Edge
Functions. Данные защищены на уровне БД через RLS, а не только маршрутами интерфейса. Выбран
он потому, что стек зафиксирован в ТЗ, а объём серверной логики мал: три-четыре операции,
каждая из которых умещается в отдельную функцию.

Генерация — **асинхронная**: запрос ставит задачу и сразу возвращает её `id`, клиент
подписывается на изменения статуса. Так перезагрузка страницы не теряет результат (NFR-02) и
не упирается в таймаут HTTP-запроса.

- **Контекст системы** — схема [V-02](VISUALS.md#v-02)
- **Контейнеры** — схема [V-03](VISUALS.md#v-03)
- **Жизненный цикл генерации** — схема [V-07](VISUALS.md#v-07)

**Точка входа:** `src/main.tsx` (React-приложение) · серверная —
`supabase/functions/*/index.ts`

**Как запускается:**

```
npm run dev
```

**Как собирается:**

```
npm run build
```

> Сборщик — **Vite**, решение принято 2026-08-27 и зафиксировано в
> [ADR-0007](adr/0007-vite-spa-no-ssr.md): приложение целиком за логином, SSR не нужен,
> а серверная логика остаётся в Edge Functions — второго места для неё не появляется.

| Слой | Выбор | Почему именно он | Откатываемо? |
| --- | --- | --- | --- |
| Язык | TypeScript | Типы контрактов между клиентом и Edge Functions + типы, генерируемые из схемы Supabase, ловят рассинхрон схемы и кода на сборке | дорого |
| Фреймворк UI | React 18+ | Зафиксировано ТЗ | дорого (ограничение ТЗ) |
| Сборка | Vite | Стандарт для React-SPA, быстрый dev-server; SSR не нужен — приложение за логином ([ADR-0007](adr/0007-vite-spa-no-ssr.md)) | дорого: переезд на SSR переносит не вёрстку, а место серверной логики |
| Бэкенд-платформа | Supabase (Postgres + Auth + Storage + Edge Functions + Realtime) | Зафиксировано ТЗ; закрывает auth, БД, файлы и серверную логику одним сервисом — отдельный бэкенд не нужен | дорого (ограничение ТЗ) |
| Хранилище данных | Postgres (Supabase) | Идёт вместе с платформой; баланс и списания требуют транзакций, а не документной БД | дорого |
| Хранилище файлов | Supabase Storage | Входные фото и результаты генераций; приватные бакеты + подписанные ссылки | легко |
| Серверная логика | Supabase Edge Functions (Deno) | Единственное место, где можно держать ключ провайдера и менять баланс | средне |
| Изоляция данных | Postgres RLS | Требование NFR-04: проверка на уровне БД, а не маршрутов интерфейса | дорого |
| AI-провайдер | **не выбран** — за абстракцией; доступ на время приёмки идёт через шлюз [AITunnel](https://aitunnel.ru/), модель `gemini-2-5-flash-image` (решение 2026-08-27) | Прямой доступ к Gemini API из РФ закрыт: страны нет в [списке доступных регионов](https://ai.google.dev/gemini-api/docs/available-regions). Шлюз — способ оплаты и доступа, а не выбор вендора: [ADR-0005](adr/0005-ai-provider-abstraction.md) в силе | легко (в этом и смысл абстракции) |
| Состояние сервера в UI | TanStack Query | Кэш, инвалидация, ретраи для списков генераций и баланса | легко |
| Стилизация | Tailwind + shadcn/ui | Код компонентов лежит в репозитории, а не в зависимости; доступность (NFR-07, WCAG AA) приходит из Radix — формы, диалоги и управление фокусом не пишутся с нуля | средне: переписывается вёрстка, но не логика |
| Деплой фронтенда | **Vercel** (решение пользователя 2026-08-27) | Статическая сборка Vite без SSR — хостингу нужны только раздача файлов и SPA-fallback; Vercel даёт их с превью на каждую ветку. Серверная логика остаётся в Edge Functions Supabase, на Vercel её не переносим | средне: сборка статическая, переезд на другой хостинг — смена CI, а не кода |

### Рассмотренные альтернативы

| Вариант | Чем был привлекателен | Почему отвергнут |
| --- | --- | --- |
| Отдельный бэкенд (Node/Nest) рядом с Supabase | Привычная серверная архитектура, легче сложная логика | Логики мало (4 операции); второй сервис = второй деплой, вторая аутентификация, второй источник правды о балансе |
| Вызов AI-провайдера прямо из браузера | Проще и быстрее в разработке | Ключ провайдера утекает клиенту, а баланс становится подделываемым — прямое нарушение NFR-05 |
| Синхронная генерация одним HTTP-запросом | Проще: ответ = результат | Генерация идёт десятки секунд; таймауты и потеря результата при F5 (NFR-02) |
| Хранение баланса числом в таблице пользователя без журнала | Меньше кода | Невозможно разобрать спор «куда делись баллы» и невозможна идемпотентность (NFR-03) |
| Next.js вместо React-SPA + Vite | SSR, серверные экшены вместо Edge Functions | ТЗ говорит «React.js»; SEO-требований у приложения за логином нет. Пересмотреть — только вместе с пользователем |

## 3. Модули и контракты

| Модуль | Ответственность | Что наружу (интерфейс) | Что внутри (скрыто) |
| --- | --- | --- | --- |
| `auth` | Регистрация, вход, восстановление пароля, выход, текущий пользователь | Хук текущей сессии + гварды маршрутов | Работа с Supabase Auth, хранение сессии, редиректы после письма |
| `catalog` | Каталог генераций пользователя, открытие прошлой генерации | Список генераций, генерация по `id` | Запросы, пагинация, кэш, подписанные ссылки на файлы |
| `generation-wizard` | Сборка параметров генерации: фото → распознавание → тип → сценарий → пожелания → количество | Объект параметров генерации | Состояние шагов, валидация, восстановление после логина (US-01) |
| `catalog-taxonomy` | Справочник 7 категорий и 24 сценариев показа | Категории; сценарии по категории | Источник справочника, превью сценариев |
| `pricing` | Цена генерации в баллах по количеству объектов и типу | Расчёт цены | Прайс-таблица. **Реализация одна на клиента и сервер** — файл `supabase/functions/_shared/pricing.ts`, клиент подключает его алиасом `@shared`. Клиентская цена показывается, серверная списывается |
| `billing` | Баланс, пакеты, история операций | Баланс, список пакетов, пополнение | Журнал операций, идемпотентность (NFR-03) |
| `generation-service` (Edge) | Приём заявки, проверка и списание, постановка задачи | `POST /generate` → `{ generationId }` | Проверка баланса, транзакция списания, запись заявки |
| `generation-worker` (Edge) | Вызов провайдера, сохранение результатов, финализация статуса и баланса | — (фоновая) | Ретраи, частичный успех (US-E5), возврат баллов при неуспехе |
| `ai-provider` (Edge) | **Абстракция провайдера**: распознавание товара, генерация изображений, тексты карточки, название генерации | `recognize(photo)`, `generateImages(params)`, `composeCard(params)`, `nameGeneration(params)` | Конкретный провайдер, промпты, формат запроса, учёт себестоимости |

**Границы, которые нельзя пересекать:**

- UI **никогда** не вызывает AI-провайдера напрямую и не знает его имени — только через
  Edge Functions. Ключи провайдера в браузер не попадают ни при каких условиях.
- UI **никогда** не пишет в баланс. Таблица баланса и журнал операций доступны клиенту только
  на чтение (RLS), изменение — только серверной логикой: Edge Function с service-role либо
  `security definer`-функция БД (стартовые баллы начисляет триггер подтверждения email —
  вызова из браузера там нет и быть не может, см. план вехи M3). Право выполнения у функции
  изменения баланса снято с `anon` и `authenticated` поимённо: в схеме `public` Supabase
  раздаёт `execute` прямыми грантами, и `revoke from public` его не снимает.
- Цена, показанная клиентом, — **справочная**. Списывается цена, посчитанная сервером;
  расхождение — ошибка, а не «клиент прав».
- Никакой модуль UI не ходит в таблицы напрямую в обход слоя данных модуля-владельца.

> Проектирование границ — скил `codebase-design`. Эти же границы проверяет ревью веток.

## 4. Данные

- **Сущности и связи** — схема [V-04](VISUALS.md#v-04)
- **Хранилище:** Postgres (Supabase). Ключевые таблицы: `profiles` (баланс), `ledger`
  (журнал операций с баллами — единственный источник правды о движении), `generations`
  (заявка, параметры, статус, название от ИИ), `generation_assets` (результаты),
  `categories`, `presets` (24 сценария показа), `credit_packages`.
- **Баланс:** хранится как поле в `profiles`, но изменяется **только** вместе с записью в
  `ledger` в одной транзакции. Каждая запись журнала несёт ключ идемпотентности, чтобы
  повторная доставка события не списала дважды (NFR-03).
- **Файлы:** Supabase Storage, приватные бакеты `uploads` (входные фото) и `results`
  (изображения генераций). Доступ — только подписанными ссылками с коротким сроком жизни.
- **Изоляция:** RLS на всех пользовательских таблицах по `auth.uid()`; на `ledger` —
  чтение своих записей, запись запрещена всем, кроме service-role (NFR-04, NFR-05).
- **Ролей нет** (решение 2026-08-27): администрирование идёт через Supabase Studio и
  service-role, справочники заводятся миграциями. Чтобы появление роли позже стоило одной
  правки, а не переписывания всех политик, условие доступа выносится в **единую SQL-функцию**,
  а не повторяется текстом в каждой политике.
- **Миграции:** файлы в `supabase/migrations/`, накатываются Supabase CLI. Откат — обратной
  миграцией, а не правкой прода руками.
- **Персональные данные:** email (Supabase Auth), пароль — только хешем на стороне Supabase.
  Фото товаров — пользовательский контент → `TZ.md` NFR-06.
- **Удаление аккаунта** (152-ФЗ, отзыв согласия): `profiles` уходит каскадом, строки `ledger`
  остаются **обезличенными** (`user_id` → NULL) — учётный регистр удаление переживает.
  Ключ идемпотентности адреса не содержит, только его отпечаток ([ADR-0009](adr/0009-ledger-survives-account-deletion.md)).
- **Резервные копии / восстановление:** > TODO(пользователь): политика бэкапов зависит от
  тарифа Supabase. Каталог генераций восстановить перегенерацией нельзя — это платный
  результат, бэкап `results` обязателен.

## 5. Интеграции

| Внешний сервис | Зачем | Протокол/контракт | Что делаем, если недоступен |
| --- | --- | --- | --- |
| AI-провайдер (не выбран) — на приёмке через шлюз AITunnel | Распознавание категории и товара, генерация изображений, тексты карточки, название генерации | **OpenAI-совместимый HTTP** из Edge Function за интерфейсом `ai-provider`: база `https://api.aitunnel.ru/v1`, ключ заголовком `Authorization: Bearer sk-aitunnel-…`; изображения — `POST /images/generations`, распознавание и тексты — `POST /chat/completions`. Базовый URL и модели задаются профилем провайдера, а не зашиты в код | Генерация помечается неуспешной, списанные баллы возвращаются, пользователю — понятная ошибка с предложением повторить (US-E4). Шлюз добавляет второе звено отказа: его недоступность обрабатывается тем же путём |
| Supabase Auth (почта) | Письма восстановления пароля и, если понадобится, подтверждения email | Встроенная отправка Supabase | Показать «письмо не отправлено, попробуйте позже»; аккаунт при этом не ломается |

**Секреты и доступы:** ключ AI-провайдера (на приёмке — ключ шлюза AITunnel) и
`SUPABASE_SERVICE_ROLE_KEY` — только в секретах Edge Functions. Ключ шлюза **не бывает**
`VITE_*`-переменной: всё с этим префиксом попадает в бандл и открыто любому посетителю. В браузер уходят исключительно `SUPABASE_URL` и `anon`-ключ, которые публичны
по устройству Supabase и безопасны **при условии корректных RLS-политик**. **Никогда — в коде
и в git** (см. `.gitignore` и канон `AGENTS.md`).

## 7. Тестирование

- **Что покрываем тестами обязательно:**
  - расчёт цены (`pricing`) — клиентский и серверный дают одинаковый результат;
  - списание, возврат и идемпотентность баллов (NFR-03) — включая повторную доставку события;
  - RLS-политики: запрос с чужим `id` получает отказ (NFR-04, NFR-05) — тест на уровне БД;
  - сценарии ошибок US-E3, US-E4, US-E5 — баланс после сбоя равен балансу до запуска;
  - главный сценарий US-01 end-to-end с заглушкой провайдера.
- **Что не покрываем и почему:** качество самих изображений — оценивается глазами по
  приёмочному критерию «товар на выходе узнаваем», автотестом не проверяется.
- **Команды прогона.** Три, потому что проверяются три разные вещи, и подменять одну
  другой нельзя (все, кроме первой, требуют поднятого `supabase start`):
  - `npm test` — код приложения;
  - `npm run test:db` — RLS-политики: их надо спрашивать у Postgres от лица чужой сессии,
    а не у приложения. pgTAP из Supabase CLI, файлы в `supabase/tests/database/`;
  - `npm run test:flow` — сценарии аккаунта против живого Auth: письма, ссылки из них и
    отказы на входе. На моках это проверять бессмысленно — мок подтвердит ровно то, что мы
    сами в него записали. Скрипт — `supabase/tests/auth-flow.mjs`.
- **Критерии приёмки** живут в `TZ.md` §9 в форме `Given/When/Then` — из них делаются тесты
  (скилы `test-driven-development`, `verification-before-completion`).

## 8. Релиз и эксплуатация

- **Как попадает к пользователю:** статическая сборка фронтенда на хостинг + `supabase
  functions deploy` для серверной части + миграции БД. Порядок обязателен: миграции →
  функции → фронтенд, иначе новый UI упирается в старую схему.
- **SPA-fallback на хостинге обязателен** — `vercel.json` с `rewrites` на `/index.html`.
  Без него любой адрес, кроме `/`, отдаёт 404 хостинга: файла `signup.html` в статической
  сборке нет, маршруты разбирает роутер в браузере. Это ломает не только прямые ссылки —
  ссылка подтверждения email ведёт на `/auth/callback`, и без fallback подтверждение на
  проде не работает вообще (найдено 2026-08-28 проверкой прода после вехи M2).
- **Конфигурация Auth на проде** — `supabase config push --project-ref <ref>`, профиль
  `[remotes.production]` в `supabase/config.toml`. Там же живёт внешний SMTP: встроенная
  почта Supabase ограничена двумя письмами в час, и на ней подтверждение email (FR-18)
  ломается на втором регистрирующемся. Провайдер — **Brevo** (300 писем в сутки бессрочно;
  решение пользователя 2026-08-28, веха M2). Секреты берутся из переменных окружения
  (`BREVO_*` в `.env.example`) и в конфигурацию не вписываются.
  > Домена у проекта пока нет. Brevo в этом случае не заваливает DMARC, а подменяет
  > видимый домен отправителя на `@brevosend.com` — письма доходят. Появится свой домен —
  > настраивается DKIM в Brevo, и адрес становится своим; правка на одну строку.
  >
  > **Лимитов на письма два, и подключение SMTP снимает не тот, о котором думаешь.** У
  > провайдера своя квота (Brevo — 300 в сутки). У самого Supabase Auth есть отдельный
  > счётчик `[auth.rate_limit] email_sent` — сколько писем он отдаст в SMTP за час.
  > Подключение своего SMTP поднимает его с 2 до 30 **только если значение не задано
  > явно**; заданное в `config.toml` уезжает на прод как есть и перекрывает поднятие.
  > Прод-значение живёт в `[remotes.production.auth.rate_limit]`.
- **Версионирование:** > TODO(пользователь): semver по тегам или просто по коммитам?
- **Наблюдаемость:** логируются регистрация, запуск генерации, списание / возврат баллов,
  вызов провайдера с длительностью и себестоимостью, ошибки провайдера — всё с

## 10. Риски

| Риск | Влияние на архитектуру | Что делаем заранее |
| --- | --- | --- |
| Провайдер не выбран | Контракт `ai-provider` строится «под неизвестного»; риск, что выбранный не покроет все четыре операции | Интерфейс задаёт четыре независимые операции — можно взять разных провайдеров под разные ([ADR-0005](adr/0005-ai-provider-abstraction.md)) |
| Себестоимость генерации неизвестна | Прайс в баллах может оказаться убыточным | Учёт себестоимости на вызов с первого дня; прайс — данные, а не константа в коде |
| Объёмы неизвестны (NFR-11) | Тариф Supabase и лимиты Storage выбраны вслепую | Бакеты и срок хранения — конфигурируемые; не завязываться на «безлимит» |
| Отсутствие эквайринга сейчас, но появление позже | Пополнение спроектировано как мгновенное | Пополнение проводить через тот же `ledger`, что и списание, — тогда добавление платежа не трогает баланс |

## 11. Handoff: как строить генеральный план

> **Этот раздел адресован модели, которая будет составлять
> [`../planning/reference/00_GENERAL_PLAN.md`](../planning/reference/00_GENERAL_PLAN.md).**
> Он существует, потому что генеральный план — самая дорогая к ошибке работа на проекте:
> ошибка в нём тиражируется во все последующие планы и коммиты.

### Протокол — исполнять по шагам

1. **Прочитать целиком:** [`TZ.md`](TZ.md) · этот файл · [`VISUALS.md`](VISUALS.md).
   Плюс канон [`../AGENTS.md`](../AGENTS.md) и карту скилов
   [`../.claude/skills/INDEX.md`](../.claude/skills/INDEX.md) (consult-first).
2. **До составления плана** — оценить работу по рубрике ниже и выдать пользователю
   рекомендацию **одной репликой**:

   > По этому ТЗ и спецификации: рекомендую **модель <X>, эффорт <Y>** — потому что
   > <1–2 строки обоснования по осям рубрики>. Переключись (`/model <X>`, при необходимости
   > смени эффорт) и напиши **«продолжить»**. Согласен с текущей моделью — тоже «продолжить».

3. **ОСТАНОВИТЬСЯ и ждать.** Не начинать генеральный план, пока пользователь не ответил.
4. **После «продолжить»** — объявить активную модель и вытекающую полосу доверия
   ([ADR-0002](adr/0002-trust-lane-by-model-not-host.md)), затем строить генеральный план по
   скилу `writing-plans`.

> Механика паузы — та же, что в [`../.claude/commands/review-branches.md`](../.claude/commands/review-branches.md)
> (шаг 1b). Вторую механику не изобретать.

### Рубрика: признак задачи → модель + эффорт

Оси оценки: **цена ошибки** · **объём кросс-файловых зависимостей** · **новизна домена** ·
**необратимость решений**.

| Признак работы | Модель | Эффорт |
| --- | --- | --- |
| Генеральный план с нуля: много модулей, необратимые решения (стек, границы, хранилище), цена ошибки высокая | **Claude Opus 5** (`claude-opus-5`) | `high` → `xhigh` |
| То же, но домен незнакомый / противоречивые требования / нужна длинная автономная проработка | **Claude Fable 5** (`claude-fable-5`) | `xhigh` → `max` |
| Один модуль, стек и границы уже зафиксированы, решения обратимые | **Claude Sonnet 5** (`claude-sonnet-5`) | `medium` → `high` |
| Механическая работа: переформатировать план, разнести пункты по файлам, свести таблицу | **Claude Haiku 4.5** (`claude-haiku-4-5`) | `low` |

### Что этому проекту важно не потерять в плане

- **Биллинг раньше красоты.** Списание, возврат и идемпотентность (NFR-03) — фундамент;
  переделывать их после запуска означает разбираться с реальными спорами о баллах.
- **RLS в той же миграции, что и таблица.** Отложенная безопасность на этом стеке не
  откладывается, а забывается.
- **Провайдер за абстракцией с первого дня** — он ещё не выбран (ADR-0005), и код не должен
  об этом знать.
- **Заглушка провайдера для local** — иначе разработка жжёт бюджет на каждом прогоне.
- **24 сценария показа — данные.** В плане это отдельная задача наполнения, а не «попутно».
