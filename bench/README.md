# Приёмочный стенд провайдера (веха M5, шаг 1)

> **Зачем он есть.** Выбор вендора — главный риск продукта ([`docs/TZ.md`](../docs/TZ.md) §10):
> если товар на выходе не похож на загруженный, продукт не нужен — ни цена, ни скорость этого
> не компенсируют. «Посмотреть на одну картинку и решить» — это не выбор, а впечатление.
> Стенд даёт всем кандидатам **один и тот же вход** и складывает выходы рядом, чтобы решение
> опиралось на выборку, а не на удачный кадр.

Стенд живёт рядом с кодом и ходит в **локальный** Supabase. В проде его нет и быть не должно.

---

## Критерий узнаваемости

**Зафиксирован до первого прогона.** Иначе он подгонится под понравившийся результат: увидев
красивую картинку, легко задним числом решить, что «предмет в общем-то тот же».

Генерация **узнаваема**, если выполнены все четыре пункта:

1. **Тот же предмет.** Не «похожий из той же категории»: кроссовок другой модели, другая
   кружка, другой флакон — это провал, даже если кадр красивее исходного фото.
2. **Сохранена форма.** Силуэт, пропорции, конструктивные детали — карманы, швы, ручки,
   крышка, застёжка. Предмет не «додуман» и не упрощён.
3. **Сохранены цвет, надписи и логотипы.** Цвет — тот же оттенок, а не соседний. Текст на
   упаковке читается и совпадает с исходным; выдуманный текст или искажённый логотип — провал.
4. **Число объектов не изменилось.** Один товар на входе — один на выходе. Пара обуви
   остаётся парой, набор из трёх банок — набором из трёх.

**Что в критерий НЕ входит** (и потому не может ни спасти, ни завалить кандидата): красота
кадра, свет, стиль, «маркетплейсность» вида, эстетика композиции. Это предмет вехи M6.
Здесь проверяется ровно одно: **тот ли это товар**.

**Пороговое правило.** Кандидат проходит, если узнаваемы **все** наборы выборки. Один провал —
находка, а не погрешность: пользователь платит баллами за каждую генерацию, и «в среднем
похоже» ему не поможет.

## Что стенд проверяет сам, а что — глазами

Машинно (в отчёте `PASS`/`FAIL`, вердикт человека не нужен):

| Проверка | Откуда требование |
| --- | --- |
| Категория принадлежит перечню или равна `NULL` | ТЗ §5.1, US-E2 |
| Категория совпала с ожидаемой в `sample.json` | FR-03 |
| Наименование товара непустое | FR-04 |
| Файл совпал с профилем пары «маркетплейс × категория»: размер и формат | FR-25 |
| Название генерации непустое и не служебное | FR-16 |
| Тексты карточки есть у `kind: card` | FR-07 |
| Распознавание уложилось в 5 с | NFR-01 |

Глазами — **только узнаваемость** по критерию выше. Отчёт `report.html` кладёт вход и выход
рядом и печатает критерий над ними; вердикт проставляется там же и выгружается кнопкой.

## Контрольная выборка

Каталог `bench/samples/<id>/`: от одного до четырёх фото (FR-02) и `sample.json` рядом.

```json
{
  "note": "мелкий предмет, блик от витрины",
  "marketplaceId": "ozon",
  "kind": "card",
  "categoryId": "tech",
  "presetId": "tech-studio",
  "productTitle": "Наушники накладные",
  "productDescription": "",
  "wishes": ""
}
```

- `categoryId` — **эталон человека**, а не подсказка провайдеру: с ним сравнивается ответ
  `recognize`. Категории — из [`docs/TZ.md`](../docs/TZ.md) §5.1.
- `presetId` — сценарий показа; обязан принадлежать `categoryId`. У категории `other`
  сценариев нет (FR-08) — там `null`, а замысел кадра уходит в `wishes` (FR-09).
- `productTitle` — что за товар на самом деле. В мастер он попадает так же, как его ввёл бы
  пользователь после распознавания.

Выборка идёт **в git**: сравнение кандидатов имеет смысл, только если вход у них буквально
один и тот же и не дрейфует между прогонами. Выходы прогонов (`bench/runs/`) — не идут.

## Прогон

Нужен поднятый локальный Supabase (`npx supabase start`).

```bash
npm run bench -- --label stub                  # вся выборка
npm run bench -- --label stub --only mug,shoes # отдельные наборы
```

`--label` обязателен: это имя кандидата в отчёте. Прогон без метки нельзя сравнить ни с чем.

Кандидат переключается **профилем провайдера, а не кодом** — переменными окружения Edge
Functions (`AI_PROVIDER`, `AI_PROVIDER_BASE_URL`, модели), после чего функции перезапускаются
и стенд гоняется снова с новой меткой. Результат — `bench/runs/<label>-<штамп>/`:

```
report.html   вход и выход рядом, критерий сверху, простановка вердиктов
report.json   машинные проверки, длительности, себестоимость — для сводки
report.md     то же коротко, чтобы вставить в ADR-0006
in/  out/     входные фото и полученные изображения
```

## Проверка самого стенда

Стенд обязан **проваливать заглушку**: она синтезирует картинку по профилю и о содержимом
входного фото ничего не знает. Прогон `--label stub`, дающий узнаваемость, означает сломанный
стенд, а не хорошую заглушку.
