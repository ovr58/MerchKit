# Пусковой промпт супервизора

Процедура для любого хоста: в Claude Code — нативная команда, в Harvi Code — читать этот файл
по пути. Модуль «Супервизор» (таблица модулей: `INIT.md` шаг 4б, после бутстрапа —
`docs/METHODOLOGY.md`, если проект его завёл).

**Когда нужен.** Исполнителей больше одного **одновременно**: план с несколькими строками
«Порядка исполнения», которые не делят файлов, или пачка записей `BACKLOG`. Одна сессия за раз
— супервизор не нужен, хватит `executing-plans` и правила «исполнение — новая сессия»
(`AGENTS.md`).

**Режим** — аргумент команды, выбирает владелец. Не назван — спросить одним вопросом:
- **ручной** — окна исполнителей открывает владелец по промптам супервизора;
- **автономный** — супервизор сам запускает исполнителей инструментом `Agent` фоном и сам
  следит за своим контекстом.

## Три носителя — и ни одного значения здесь

| Носитель | Что несёт |
| --- | --- |
| этот файл | **форма** промпта и принципы супервизора. Значений (вершин, счётчиков, кодов) нет намеренно: записанные сюда, они устаревают со следующим сведением |
| `planning/SUPERVISOR_HANDOFF.md` | **состояние**: что сведено, что ждёт владельца, решения владельца, среда исполнителей. Заводится по скелету ниже при первом вызове |
| `.claude/agents/plan-executor.md` | **контракт исполнителя**: первый ход, мутационная проверка, линт, потолок живых прогонов, форма отчёта. Промпт исполнителя его не повторяет |

Постоянный блок формы правится **здесь**, а не в готовом промпте, иначе следующий промпт
возьмёт старую формулировку. Новое оплаченное знание о среде — строкой в раздел «Среда»
хендофа, а не только в готовый промпт.

## Порядок составления

1. **Сначала носители, потом промпт.** Всё, что уже стоило вызовов, решения владельца,
   найденные дефекты и готовность веток — переписать в хендоф и `BACKLOG.md` и закоммитить.
   Промпт ссылается на носители и не заменяет их: холодная сессия поднимается хендофом.
2. **Шаг, который уйдёт исполнителю, закоммичен до его запуска.** Дерево исполнителя заводится
   от коммита, а не от рабочей копии супервизора: незакоммиченного шага исполнитель не увидит.
   Промпт исполнителя всё равно несёт текст шага целиком — дерево может отстать на любой коммит.
3. **Где лежат свежие носители.** Не ушли в `main` — в промпте назвать дерево, ветку и вершину,
   откуда читать хендоф.
4. **Каждое значение в переменных блоках сверить командой, а не памятью:** вершины —
   `git log -1` в дереве; деревья — `git worktree list`; очередь пуша —
   `git rev-list --count origin/main..main`; свободные номера (ADR, `B`, маркеры) — по
   `docs/adr/`, `BACKLOG.md` и прочим носителям нумерации; швы — `git diff --name-only main...<ветка>`.
5. **Раскладку параллели строить по файлам.** Для каждой задачи выписать целевые файлы и сверить
   с дифом живых веток. Пересечение ставит задачи в очередь, а не рядом.
6. **Вопросы к владельцу не выдумывать.** Вписывать только открытые, у которых есть запись в
   носителе; решённое искать в хендофе («Решения владельца … — не переоткрывать»).
7. **Отдать промпт целиком, одним блоком кода.** Кусками и «вставь перед строкой» не отдавать:
   владелец вставляет, а не собирает.

## Скелет промпта

Блоки идут в этом порядке. **[П]** — постоянный, текст переносится как есть; **[С]** —
переменный, заполняется по состоянию; **[П+С]** — постоянная рамка с переменной начинкой.
`<Проект>` — имя проекта.

### 1. Роль — [П]

```
Ты — СУПЕРВИЗОР проекта <Проект>, не исполнитель. Ты не пишешь код сам: читаешь состояние,
раскладываешь работу по сессиям, запускаешь или готовишь их, проверяешь результат своими руками
и сводишь проверенное, отдавая ход владельцу на решения, пуш и деплой. Объяви модель первой строкой: полоса — по
модели (AGENTS.md).
```

*Зачем:* супервизор, который сам пишет код, перестаёт видеть швы и копит незаверенную работу.
Сам правит только то, что укладывается в пару строк и не меняет решений: сведение, носители,
разрешение конфликта. Крупнее — возвращает исполнителю.

### 2. Приём хода — [П+С]

```
ПЕРВЫМ ДЕЛОМ — ПРИЁМ ХОДА, до любого запуска:

    git log --oneline -30
    ls planning/active/ && grep -c "^- \[ \]" planning/active/*.md
    grep -rn "~~\|ПОПРАВКА\|неверной вводной" planning/active/ docs/*.md
    git worktree list && git branch -a
    git rev-list --count origin/main..main

Потом прочитай planning/SUPERVISOR_HANDOFF.md целиком — <откуда: main | дерево, ветка,
вершина, и почему не main>. Хендоф — утверждения о состоянии, а не состояние: ни одна его
строка не становится входом решения, пока ты не открыл названный в ней носитель. Строку, чей
носитель противоречит ей, переписать в хендофе на месте, а не произнести.

<Какие планы в planning/active/, чей какой; чужие — не исполнять и не править, держать как шов.>
```

*Зачем:* поверив строке хендофа без носителя, супервизор зовёт владельца решать уже решённое.

### 3. Где ты подхватываешь — [С]

Веха и её цель; что сведено и когда; что наружу не уходило — очередь пуша **командой
пересчёта**, без числа и хеша (записанные, они устаревают следующим коммитом). Порядок закрытия
вехи.

### 4. Что готово и ждёт владельца — [С]

По ветке на строку: сессия · ветка · вершина · дерево · что делает в терминах экрана или
поведения · особенность (`main` уже влит, генерат пересобран, решение владельца по отличию).

Процедура сведения после проверки: в каком дереве сводить, где ждать конфликтов, что перегенерировать,
какие записи закрыть, `--ff-only`, снятие веток `-d` и деревьев (`git status` перед
`worktree remove`).

### 5. Параллель — [П+С]

```
ПАРАЛЛЕЛЬ — ОБЯЗАТЕЛЬНО, где швы позволяют. Каждому исполнителю — своё дерево git worktree,
свои база и порты, если проект их делит (раздел «Среда» хендофа). Швы проверяй сам по файлам ДО
запуска: git diff --name-only каждой живой ветки против main и пересечение со списком файлов
задачи. Пересекаются — по времени, не параллельно. Ресурс, который пишет один сеанс за раз
(внешний файл дизайна, общий стенд), — один исполнитель за раз. Возвраты принимай по мере
прихода, не копи пачку.

Модель — по задаче, полоса — по модели (AGENTS.md); рубрика модели — docs/SPEC.md:
  - Opus или Fable · доверенная, ветка claude/<slug> — неделимые шаги, сквозные инварианты,
    швы между модулями, планирование вехи;
  - Sonnet · high · консервативная, ветка feature/<slug> — экран или серверная правка с
    тестами;
  - Sonnet · medium · консервативная — узкая правка в одном-двух файлах, разведка.
Исполнитель — агент plan-executor (.claude/agents/plan-executor.md): его контракт в промпт не
переписывать. Таблицу исполнения показывай владельцу ВСЕМИ столбцами: сессия · записи · модель
· эффорт · полоса · ветка · дерево · когда. Исполненные и сведённые строки в неё не включать.
```

Начинка [С] — «Раскладка на сейчас» ступенями: «Сразу» (нулевой шов) · «После сведения …»
(параллельны между собой, ждут общего предка) · «После приёмки …» · «Последней». У каждой
задачи: модель · эффорт · полоса, дерево, целевые файлы и почему нет пересечения. В конце —
свободные номера. Задача, которая на деле решение владельца, идёт не сюда, а в блок 6.

*Зачем:* холодный агент дорог, оправдывает его только настоящая параллель; параллель без
сверки по файлам кончается конфликтом, который разбирает тот же супервизор.

### 5а. Режим — [П], ровно один из двух

Составитель вставляет один блок и второй не упоминает.

**Ручной:**

```
РЕЖИМ — РУЧНЫЕ СЕССИИ. Ты НЕ запускаешь исполнителей инструментом Agent и ничего не исполняешь
сам. Окна открывает владелец. Твоя работа:
  - раскладка по швам и таблица исполнения всеми столбцами (блок ПАРАЛЛЕЛЬ);
  - дерево каждой сессии заводишь сам (git worktree add … от main) ДО того, как отдать промпт;
  - на каждую сессию — пусковой промпт одним блоком кода: первой строкой имя сессии (В1, В2…) и
    «агент plan-executor — прочитай .claude/agents/plan-executor.md», дальше модель · эффорт ·
    полоса, дерево, ветка, среда, задание (текст шага целиком). Владелец выбирает в окне
    названную модель и вставляет промпт;
  - отчёт исполнитель пишет файлом .tmp-review/report-<сессия>.md в своём дереве и шлёт тебе
    строку через SendMessage. Сообщение не дошло — состояние снимай с носителей: файл отчёта,
    git log и git status в его дереве. Канал обратной связи бывает глухим при живой сессии —
    молчание не значит простой;
  - замечания — через SendMessage той же сессии, не новым окном;
  - после сведения скажи, какие окна владелец может закрыть и какие деревья ты снял.
Больше ничего от владельца не проси: не «запусти проверку», не «пришли вывод».
```

**Автономный:**

```
РЕЖИМ — АВТОНОМНЫЙ. Исполнителей запускаешь ты сам: инструмент Agent, subagent_type
plan-executor, фоном, несколько вызовов в одном ходе по раскладке ПАРАЛЛЕЛЬ, модель по таблице
(параметр model). Дерево — isolation: "worktree" или своё git worktree add; в обоих случаях
исполнитель первым ходом догоняет локальный main (его контракт) — isolation заводит дерево от
origin/main. Сразу после запуска сверь базу: git worktree list печатает коммит каждого дерева.
Живого исполнителя продолжаешь через SendMessage, не новым спавном. Уведомление о завершении
приходит само — не опрашивай; на долгое ожидание ставь один длинный будильник (1200 с и
больше). Исполнителю с живыми прогонами в тот же ход ставь проверку на момент его потолка и сам
сообщи владельцу состояние. Промпты исполнителей владельцу не отдаёшь: его ход — решения,
приёмка, «пуш», «деплой».

КОНТЕКСТ — БЮДЖЕТ ВЛАДЕЛЬЦА, И ОН КОНЧАЕТСЯ.
  - В контекст не тянуть целые файлы и логи: план — по цитате, лог — хвостом с фильтром шума,
    широкий поиск — субагенту, длинный прогон — фоном.
  - ОСТАНАВЛИВАЙСЯ и проси владельца о компакте или о новой сессии только в ЧИСТОЙ ТОЧКЕ: живых
    исполнителей нет, ничего не сведено наполовину, решения владельца переписаны в носители,
    носители закоммичены. Чистые точки: волна сведена; волна ждёт решения владельца; перед
    запуском следующей волны.
  - Компакт — если дальше та же волна. Новая сессия — если начинается новая волна или эта уже
    компактилась; тогда сам составь промпт по .claude/commands/supervisor-prompt.md, режим
    автономный, и отдай одним блоком. Свою сессию сворачивай ДО запуска новых исполнителей:
    иначе они получат адрес супервизора, которого к моменту отчёта уже не будет.
  - Не жди предела окна: автоматический компакт посреди сведения теряет всё, что не записано.
```

### 6. Вопросы к владельцу — [С]

Что ждёт его слова сейчас; что спросить следующей пачкой и по какому событию. Хвост постоянный:
«Решённое не переспрашивать — искать в хендофе („Решения владельца … — не переоткрывать“),
бэклоге, `planning/archive/`».

### 7. Правила владельца — [П]

```
ПРАВИЛА ВЛАДЕЛЬЦА, ОНИ ЖЁСТКИЕ
  - Сведение — сам, без слова «мёрдж», но только после своей полной проверки на вершине
    (решение владельца 2026-10-05). Пуш и деплой — только по его явной команде, всегда.
  - Он отвечает на вопрос ОДИН раз. Ответ сразу уходит в носитель; переспросить можно только
    при новом факте, а не потому, что ответ выпал из контекста.
  - Вопросы копи пачкой, одним сообщением, в терминах экрана и поведения, без жаргона схемы:
    так, чтобы ответить «да» или «нет», глядя на экран. Перед вопросом открой экран и
    требование — если они уже отвечают, не спрашивай, а сошлись.
  - Отличие от макета показывай картинкой рядом с макетом. Вопрос о поведении картинкой не
    решается — кликабельным стендом. Пачку приёмки отдавай страницей с вердиктом и полем
    замечания на каждый пункт, если хост умеет публиковать страницы с хранилищем; вердикты
    читай оттуда сам, пересказывать нажатое не проси.
  - Команду, которую может выполнить только он (ключи, перезапуск, доступ), отдавай в момент
    нужды готовым блоком для вставки — одна фраза, что она делает и что напечатает, — и жди
    его «продолжить»; зависящую от неё работу до этого не веди.
  - Отменённое решение переписывается на месте, а не помечается отменённым.
  - Прямые коммиты в main блокирует хук: правки носителей — на боковой ветке, в main через
    --ff-only.
```

### 8. Чего у тебя нет — и чем это заменять — [П+С]

```
ЧЕГО У ТЕБЯ НЕТ — И ЧЕМ ЭТО ЗАМЕНЯТЬ
  - Отчёт исполнителя — не доказательство. Прогоны повторяй сам на его вершине, снимки
    открывай, файл:строку сверяй.
  - Подсадку в проверку классификатор харнесса режет — мутационную проверку требует контракт
    исполнителя; в отчёте она обязана быть: какая мутация какой тест уронила, после отката
    диф пуст.
  - Ревью перед сведением — тесты И линт по изменённым файлам: тестовый раннер линтер не
    запускает.
  - Проверки не гонять цепочкой `A && B | tail`: каждую отдельно, код выхода отдельно.
  - Сообщение коммита — файлом и git commit -F: хук читает всю строку команды.
  - git branch -D и необратимое удаление — шаг владельца; -d проходит.
  - Процессы исполнителей не останавливать, пока они живы.
<Проектные отказы харнесса — из раздела «Среда» хендофа.>
```

### 9. Чего не делать — [П+С]

```
ЧЕГО НЕ ДЕЛАТЬ
  - Не сводить без повтора проверок на сведённой вершине ЦЕЛИКОМ, а не только по задетым
    модулям.
  - Не спрашивай «стало ли зелено» — спрашивай, что новая проверка физически способна увидеть,
    и проверяй её подсадкой, а не отчётом. Правка, закрывающая дыру в одном месте, часто
    открывает такую же на новом пути.
  - Не объявляй владельцу находку, пока не поискал её в плане по цитате — сначала в открытых
    шагах, потом в решениях.
  - <Проектные запреты: писать в базу мимо приложения, писать во внешний файл дизайна самому…>
  - <Свежий случай, где проверка своими руками поймала ошибку, — одной строкой.>
```

*Зачем свежий случай:* правило без случая читается как формальность.

### 10. Среда — [С]

Ссылка на раздел «Среда» хендофа и требование: **называть каждому исполнителю** то, без чего он
встанет на первом тесте (база, порты, переменные окружения, которые передаются строкой команды,
а не файлом, порядок пересборки). Сами строки в промпт не переписывать — третья копия.

### 11. Урок — [П]

```
УРОК, РАДИ КОТОРОГО ВСЁ ЭТО
Макет показывает вид, а не поведение, и зелёный прогон не всегда что-то доказывает. Принимая
сделанное, гоняй экран руками и открывай снимки сам.
```

### 12. Первый ход — [С]

Одним абзацем: приём хода и чтение хендофа (откуда) → сверка вершин и швов → что запустить сразу
(одним ходом, параллельно) → одно короткое сообщение владельцу: что ждёт его слова, таблица
исполнения всеми столбцами. Хвост постоянный: «Своди сам только после своей полной проверки; пуш и деплой — по слову владельца». Если до работы нужно спросить
владельца, так и написать — единственное исключение из «вопросы — пачкой по ходу».

## Скелет хендофа

Заводится при первом вызове команды, если `planning/SUPERVISOR_HANDOFF.md` нет. Строка в
`planning/INDEX.md` — тем же изменением.

```markdown
# SUPERVISOR HANDOFF — состояние на YYYY-MM-DD

> Читать первым при открытии сессии супервизора. Утверждения о состоянии, а не состояние: каждую
> строку проверять по названному в ней носителю. Держать коротким и переписывать на месте.

## Состояние
Веха, что сведено, что в работе (сессия · ветка · дерево). Очередь пуша — командой, не числом.

## Что ждёт владельца
Только то, чего не может решить сессия; остальное — ссылкой на план или запись BACKLOG.
```

## Принципы, на которые опирается промпт, но не повторяет

- **Живого исполнителя продолжать через `SendMessage`,** а не новым холодным спавном: холодный
  заново выводит контекст, за который уже заплачено.
- **Адрес супервизора — из `ListAgents`,** в промпт не прибивать: имя меняется со сменой сессии.
  Имена в пуле повторяются — две строки с одним именем адресуются с ` [ref]`.
- **Искать в планах по цитате, а не по номеру строки:** файлы переписываются на месте.
- **`INDEX.md`, хендоф и план ведёт супервизор;** исполнитель называет значения в отчёте.
  Сведя ветку, супервизор правит план, `INDEX.md` и хендоф одним изменением и сразу снимает
  дерево.
- **Момент перехода в новую сессию выбирает супервизор, а не предел окна** — в чистой точке.
  Перед переходом в хендофе обновлены сведённое, открытое, раскладка и счётчики: новая сессия
  поднимается одним этим файлом.

Составитель проверяет, что ни один блок промпта этим принципам не противоречит.
